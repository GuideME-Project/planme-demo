# 글로벌 2단계 항공 연동 준비

항공권은 별도 홈 검색 기능이 아니라 여행 일정의 참고 정보입니다. 현재는 항공 조회 모듈과 일정 대시보드 내부 표시 컴포넌트를 준비했으며, 해외 일정 생성은 여전히 준비 안내로 종료합니다.

## 활성화

서버 전용 `PLANME_GLOBAL_FLIGHTS_ENABLED=1`일 때만 `prepareTripFlights`가 조회를 허용합니다. 기본값은 비활성화입니다. 토큰은 서버 전용 `TRAVELPAYOUTS_API_TOKEN`이며 공개 환경변수로 지정하지 않습니다. 비활성·동일 국가·입력 오류는 공급자를 호출하기 전에 반환합니다.

글로벌 2단계에서는 다음 연결 작업을 완료한 후 설정을 켭니다. 주석 처리된 코드를 해제하는 방식이 아니므로 현재도 타입·빌드 검사를 받습니다.

1. `planme-search-actions.ts`의 해외 준비 안내 분기를 실제 해외 일정 생성으로 확장합니다. 현재 입력에는 여행 기간만 있고 여행 출발 날짜가 없습니다.
2. 실제 출발 날짜와 서버에서 확인한 출발/도착 국가 및 IATA 코드를 확보합니다. AI가 도시명으로 공항 코드나 날짜를 추측해서는 안 됩니다.
3. 기존 일정 생성 요청 제한 안에서 `prepareTripFlights`를 한 번 호출합니다. 공급자 조회에 8초 상한이 있으며 실패 시 일정 전체를 실패시키지 않고 항공 정보 미확인으로 처리합니다.
4. 반환된 항공편 목록을 AI의 참고 문맥에 전달합니다. AI가 편명·가격·시간·링크를 새로 만들거나 수정하지 않도록 항공 항목은 원본 구조로 유지합니다.
5. 항공 문맥을 일정에 저장하고 인라인 결과·새로고침·공유 페이지에서 `ItineraryDashboard.flightContext`에 동일하게 전달합니다. 이 저장/공유 연결은 아직 존재하지 않는 해외 일정 생성 구현과 함께 해야 합니다.
6. 설정을 켠 상태의 통합 검증 후 공개합니다. 설정만 켜도 현재 해외 검색 차단이 해제되거나 새 조회가 시작되지는 않습니다.

## 데이터와 표시

공식 명세: https://support.travelpayouts.com/hc/en-us/articles/203956163-Aviasales-Data-API

`prices_for_dates`의 편도 USD 검색 캐시를 사용합니다. 실제 공항 코드, 항공사·편명, UTC 오프셋 포함 출발 일시, 가는 편 소요 시간(있을 때만), 경유 횟수, 참고 가격과 Aviasales 검색 결과 링크를 표시합니다. 최근 48시간 이용자 검색 결과이며 실시간 가격/예약 확정이 아닙니다. `queriedAt`은 플랜미 조회 시각으로 캐시 수집 시각이 아닙니다. `return_at`이나 링크 내부 문자열로 도착 시각을 추출하지 않습니다.

결과는 비활성(disabled), 국내·동일 국가 제외(not_applicable), 조건 부족(invalid_request), 공급자/설정 오류(unavailable), 빈 결과(empty), 참고 항공편 존재(ready)로 구분합니다. 비활성 또는 제외 상태는 화면에 아무것도 표시하지 않습니다. 빈 결과는 매진으로 표시하지 않습니다.

공개 API나 홈 검색 폼은 추가하지 않았으며 현재 국내 일정 생성·해외 준비 안내 동작은 유지합니다. DB 스키마 변경 및 운영 배포는 없습니다.

## 검증 명령

- `npx --no-install tsx --tsconfig apps/web/tsconfig.json apps/web/scripts/check-trip-flights.ts`
- 토큰을 설정한 경우: `npx --no-install tsx --tsconfig apps/web/tsconfig.json --env-file=apps/web/.env.local apps/web/scripts/check-trip-flights.ts --live`
- `npm run build`
- 변경 파일에 대한 ESLint

과거 실제 호출 성공 기록과 이번 모듈의 검증은 구분해야 합니다. 실시간 Search API는 사용하지 않습니다.

## 이번 검증 결과

기본 비활성화·국내 제외·날짜/코드 검증 및 비활성 상태의 빈 렌더링 검사를 통과했습니다. MUI 스타일 속성 오류를 수정한 뒤 Next.js 빌드·타입 검사를 통과했습니다. 새 모듈 린트 오류는 없으며, 기존 대시보드 파일에는 변경 영역 밖의 경고 3개가 남아 있습니다. 이번에는 토큰을 재설정하거나 실제 공급자를 다시 호출하지 않았습니다. 글로벌 생성·AI 문맥 주입·저장/공유를 포함한 통합 검증은 2단계에서 수행합니다.

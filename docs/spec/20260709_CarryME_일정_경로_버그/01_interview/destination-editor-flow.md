# 행선지 편집 전체 이동 흐름

## 목적

- 이 주제를 확인하는 이유: 행선지 편집 화면에서 첫 방문지가 `출발지`로 표시되면 전체 여행 출발지, 현지 방문지, 숙소, 복귀지가 서로 섞인다.
- 이 주제가 불명확하면 생기는 리스크: 1박 일정에서는 우연히 맞아 보이더라도 2박 이상 일정에서 일자별 출발 기준, 숙소 이동, 마지막 날 복귀가 다시 깨진다.

## Questions

1. 행선지 편집은 방문지만 편집하는 목록인가, 일자별 전체 이동 흐름인가?
2. 1일차 출발지는 무엇으로 잡는가?
3. 2일차 이상 출발 기준점은 무엇으로 잡는가?
4. 마지막 날 복귀지는 무엇으로 잡는가?
5. 숙소는 행선지 편집에서 어떤 역할 라벨로 보이는가?
6. 행선지 역할은 AI와 코드 중 누가 정하는가?
7. AI가 제안한 장소에 좌표가 없을 때 새 좌표 시스템을 만들 것인가, 기존 장소 검색 흐름을 태울 것인가?
8. 경로 다시 계산은 무엇을 의미하는가?

## Answers

1. 행선지 편집은 일자별 전체 이동 흐름 편집으로 확정했다.
2. 1일차 출발지는 사용자가 처음 입력한 전체 여행 출발지다. 예: `서울 마포구`.
3. 2일차 이상은 AI가 명시한 그날의 출발 기준점을 우선하고, 누락 시 전날 마지막 숙소 이벤트/숙소 지점을 기본값으로 본다.
4. 마지막 날 복귀지는 처음 출발지다. 예: `서울 마포구`.
5. 숙소는 그날 마지막 행이어도 항상 `숙소`로 표시한다.
6. 행선지 역할은 AI가 stop별 role로 내려준다. 코드는 index나 이름으로 `출발지`, `숙소`, `복귀지`를 적극 추론하지 않는다.
7. AI가 제안한 장소에 좌표가 없으면 기존 장소 검색/상세 조회 흐름을 사용해 좌표를 확정한다.
8. 경로 다시 계산은 API를 통해 이동 시간과 지도에 표시할 provider polyline/path를 다시 받는 것이다.

## Score

- 현재 불명확성 점수: `0.14`
- 목표 임계값: `Standard 0.20`
- 점수 근거: 행선지 편집의 업무 의미, 포함해야 할 역할, 1박/2박 이상의 출발/복귀 기준, 좌표 보강 방식이 확정됐다.
- 다음에 낮춰야 할 불확실성: AI 출력 필드명을 기존 `standardStops`/`carrymeStops`에 role을 추가하는 방식으로 할지, 행선지 편집 전용 구조를 별도로 둘지 설계 단계에서 정리한다.

## Confirmed

- 행선지 편집은 단순 방문지 목록이 아니다.
- 행선지 편집은 일자별 전체 이동 흐름이다.
- 행선지 편집 목록에는 `출발지`, `방문지`, `숙소`, `복귀지`가 모두 들어간다.
- 1일차 출발지는 처음 입력한 전체 여행 출발지다.
- 마지막 날 복귀지는 처음 입력한 전체 여행 출발지다.
- 2일차 이상 출발 기준은 AI 명시값을 우선하고, 누락 시 전날 마지막 숙소 이벤트/숙소 지점을 사용한다.
- 숙소 role은 항상 `숙소`로 표시한다.
- CarryME의 `짐 숙소 도착`은 타임라인 이벤트다. 행선지 편집의 숙소 role과 섞지 않는다.
- AI가 각 행선지 stop에 역할을 내려준다.
- AI가 role을 누락하거나 유효하지 않게 주면 코드가 임의 보정하지 않고 `확인 필요` 상태로 보고 경로 재계산을 막는다.
- 코드가 index만 보고 첫 행을 `출발지`, 마지막 행을 `도착지`로 해석하는 방식은 이번 버그의 직접 원인이다.
- 좌표 보강은 새로 만들지 않고 기존 장소 검색/상세 조회 흐름을 재사용한다.
- 좌표가 없는 행선지가 있으면 provider 경로 계산 전에 막는다.
- 경로 다시 계산은 화면 행선지 흐름을 기준으로 API를 호출해 시간과 지도 path/polyline을 갱신하는 것이다.

## Current Code Findings

- 현재 `createDestinationRows`는 CarryME route의 `stops`만 편집 rows로 만들고, stop의 역할 정보를 보존하지 않는다.
- 현재 `getDestinationRole`은 index가 0이면 무조건 `출발지`, 마지막이면 무조건 `도착지`로 표시한다.
- 현재 생성 데이터의 `carryme.stops`가 부산 내부 방문지부터 시작하면 첫 방문지가 `출발지`로 보인다.
- 현재 `requestRouteCheck(rows)`는 rows 전체를 경로 계산 입력으로 보고, 인접한 두 row를 구간 단위로 계산한다.
- 자동차 구간은 Naver Directions API를 사용한다.
- 대중교통/도보 구간은 ODsay를 사용한다.
- 코드에는 이미 좌표 누락 방어가 있다. 좌표 없는 row가 있으면 경로 계산 전에 `검색 결과에서 장소를 선택해 주세요` 메시지로 막는다.
- 화면 편집 단계에는 이미 `/api/places/autocomplete`와 `/api/places/details`를 통한 장소 검색 및 좌표 확정 흐름이 있다.
- 생성 단계에는 숙소 후보를 검색하고 실제 숙소명/좌표를 route stop과 timeline에 반영하는 흐름이 있다.

## Open Questions

- AI 출력 계약은 기존 `standardStops`/`carrymeStops`에 `role`을 추가하는 방식으로 갈지, 행선지 편집 전용 `routeRows` 같은 새 구조를 둘지 설계 단계에서 정한다.
- `startPoint` 필드는 이전 인터뷰에서 한 번 확정됐으나, 이후 행선지 편집이 전체 이동 흐름으로 재정의됐다. 설계 단계에서는 별도 `startPoint`와 첫 stop `role: 출발지`의 중복 여부를 정리해야 한다.
- role이 누락된 기존 Redis preview는 직접 수정하지 않는다는 기존 결정이 유지된다. 새 생성/새 미리보기부터 계약을 적용한다.
- 질문이 필요한 주제는 사용자에게 묻기 전에 서브 에이전트로 적합성 검토를 먼저 거친다.

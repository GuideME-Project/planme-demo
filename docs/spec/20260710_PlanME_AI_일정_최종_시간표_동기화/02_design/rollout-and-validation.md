# 배포·롤백·검증 설계

## 결론

- 코드, 내부 인증값, 웹·MCP 배포를 하나의 완료 조건으로 관리한다.
- 원본 `main`과 이번 구현 워크트리의 앱별 환경파일만 갱신하고 과거 워크트리는 제외한다.
- Vercel 직접 배포를 사용하지 않고 PR 병합에 따른 자동 배포를 사용한다.
- 새 일정, 기존 링크, ChatGPT 위젯, 상세 웹을 모두 운영 환경에서 검증한다.

## 환경변수 반영

추가할 서버 비밀값:

```text
PLANME_INTERNAL_API_TOKEN
```

로컬 반영 대상:

```text
원본 main/apps/mcp/.env.development
원본 main/apps/mcp/.env.local
원본 main/apps/web/.env.development
원본 main/apps/web/.env.local
이번 구현 워크트리/apps/mcp/.env.development
이번 구현 워크트리/apps/mcp/.env.local
이번 구현 워크트리/apps/web/.env.development
이번 구현 워크트리/apps/web/.env.local
```

반영 원칙:

- 강한 임의 값을 한 번 생성해 모든 대상에 동일하게 사용한다.
- 값은 터미널, 문서, Git diff, 테스트 로그에 출력하지 않는다.
- 원본 `main`의 앱별 환경파일을 기준으로 구현 워크트리에 런타임 파일을 복사한다.
- 과거 등록 워크트리에는 복제하지 않는다.
- Git 추적 여부를 확인해 `.env*`가 커밋되지 않게 한다.

Vercel 반영 대상:

- `planme-demo`: Production, Preview
- `planme-demo-mcp`: Production, Preview

브라우저의 기존 로그인 세션을 사용해 같은 값을 등록하고, 값 자체는 보고서에 남기지 않는다. Development는 로컬 `.env` 파일로 관리한다.

## 배포 순서

1. 원본과 구현 워크트리에 런타임 환경파일을 준비한다.
2. 로컬에서 동일 인증값으로 웹·MCP 통합 흐름을 검증한다.
3. Vercel 두 프로젝트의 Production·Preview에 인증값을 추가한다.
4. 코드 PR을 생성하고 `main`에 병합한다.
5. 웹과 MCP 두 Vercel 배포가 모두 성공할 때까지 확인한다.
6. 두 배포가 모두 준비된 뒤 ChatGPT와 상세 웹 운영 테스트를 시작한다.

웹과 MCP의 배포 완료 시점이 다르면 그 사이 일정 생성은 실패할 수 있다. 이 구간에는 AI 예상 이동 시간으로 되돌아가지 않고 재요청 안내를 사용한다.

## 기존 데이터 전환

- 버전 1 Redis 일정은 삭제하지 않는다.
- 상세 링크 최초 접근 시 최종 경로 계산을 시도한다.
- 성공하면 버전 2로 원자적 교체하고 기존 만료 시각 범위 안에서 저장한다.
- 실패하면 버전 1을 유지하고 AI 예상 이동 시간을 최종값으로 표시하지 않는다.
- 과거 ChatGPT 위젯은 변경하지 않는다.

별도 DB 마이그레이션은 없다. Upstash Redis 저장 래퍼 버전만 확장한다.

## 롤백

- 코드 롤백은 이전 `main` 커밋으로 되돌리는 PR을 사용한다.
- 버전 2 저장 데이터는 버전 1 읽기 코드가 무시하거나 안전하게 파싱하도록 하위 호환 읽기를 유지한다.
- `PLANME_INTERNAL_API_TOKEN`은 롤백 직후 삭제하지 않아도 동작에 영향을 주지 않지만, 새 구조를 폐기하면 두 Vercel 프로젝트와 로컬 환경파일에서 함께 제거한다.
- 롤백 시에도 AI 예상 시간과 제공자 이동 시간을 섞어 저장하지 않는다.

## 자동 검증

### 구현 사전 중단 조건

- 현재 ODsay 키로 웹 서버 런타임에서 실제 대중교통 경로를 한 건 호출한다.
- 정상 이동 시간과 구간 응답을 받으면 서버 이전을 진행한다.
- URI 제한 오류가 발생하면 브라우저 호출을 억지로 우회하거나 자동차 결과를 복사하지 않는다.
- 서버 사용이 가능한 ODsay 키 또는 제공자 설정이 준비될 때까지 대중교통 서버 최종화 구현·배포를 중단하고 보고한다.

### 핵심 계산

- 자동차 한 일차 Standard·CarryME의 네이버 구간 시간 합산
- 대중교통 한 일차 Standard·CarryME의 ODsay 구간 시간 합산
- 2일 이상 모든 일차 계산 완료
- 관광·식사·체류 시간이 총 이동 시간에 포함되지 않음
- AI 시간표 배열이 계산 전후 동일함
- 연속 동일 장소 제거 후 출발지·도착지 동일 오류가 발생하지 않음
- 실패 구간 1회 재시도
- 전체 40초 초과 시 중간 결과 미저장

### API·저장

- 정상 내부 인증값으로 최종 계산·저장 성공
- 인증값 누락·불일치 시 401
- 일부 경로 실패 시 422와 기존 저장값 유지
- 기준 버전 충돌 시 409
- 저장 실패 시 최종 위젯 준비 상태를 반환하지 않음
- 버전 1 읽기와 버전 2 읽기 호환
- 지도 구간 형상을 저장한 뒤 다시 읽어 동일하게 복원

### UI·위젯

- 일정 생성 도구 실행 중 위젯이 표시되지 않음
- 성공 후 최종 위젯이 정확히 한 번 표시됨
- 위젯과 상세 웹의 Standard·CarryME 총 이동 시간이 동일함
- 상세 웹 최초 렌더링 뒤 2~3초 후 시간이 바뀌지 않음
- 1일차·2일차 최초 및 반복 전환에서 재계산 요청이 발생하지 않음
- 네이버 경로가 준비되기 전 직선 경로가 표시되지 않음
- 상세 지도 높이와 지도 표면 높이가 일치함
- 편집 재계산 실패 시 마지막 성공 결과로 복원

## 운영 수동 검증

1. ChatGPT에서 동탄 출발, 부산 또는 경주 1박 2일 자동차 일정을 생성한다.
2. 위젯이 생성 중 반복 표시되지 않고 최종 한 번만 나타나는지 확인한다.
3. 위젯의 Standard·CarryME 이동 시간을 기록한다.
4. 상세 일정을 열어 같은 이동 시간인지 확인한다.
5. 각 일차 탭과 상세 지도 탭을 처음과 두 번째로 전환한다.
6. 시간 변경, 직선 경로 점멸, 중복 숙소 경로, 동일 출발지·도착지 오류가 없는지 확인한다.
7. 대중교통 일정에서도 이동 시간과 제공 가능한 지도 경로를 확인한다.

## 관측성과 로그

구조화 로그에 다음 항목만 남긴다.

- 요청 식별자
- 일정 식별자
- 일차와 경로 종류
- 이동 수단
- 계산 소요 시간
- 재시도 횟수
- 성공·실패 코드
- 저장 버전

장소 전체 일정 본문, 인증값, 제공자 키는 로그에 남기지 않는다.

운영 확인 지표:

- 최종 계산 성공률
- 40초 초과 비율
- 경로별 평균 계산 시간
- 제공자별 실패율
- 위젯 조회 실패율
- 기존 일정 버전 2 전환 성공률

## 남은 리스크

- 대중교통 장거리 구간은 지도 형상이 부분 제공될 수 있다.
- 경로 형상 때문에 Redis 값 크기가 증가하므로 실제 2박 3일 payload 크기를 측정해야 한다.
- Vercel 두 프로젝트가 같은 커밋을 서로 다른 시점에 배포하므로 운영 테스트 시작 전에 두 상태를 모두 확인해야 한다.

# 장소 교체 오케스트레이션

## 목적

웹이 발견한 대중교통 접근 실패를 MCP의 AI 장소 생성 문맥으로 안전하게 되돌려, 한 장소의 실패가 전체 일정의 422 응답으로 끝나지 않도록 한다.

## 책임 분리

| 구성요소 | 책임 |
| --- | --- |
| MCP·`planme-core` | 사용자 의도 정규화, 지역 범위, 고정 장소 보존, AI 장소 생성·교체·제거 |
| 웹 저장 API | ODsay·네이버 경로 계산, 고정 장소의 정류장·도보 보정, 경로 최종화, 원자적 저장 |
| 상세 화면 | 저장된 최종 경로·시간표 표시, 추정 상태에 따른 절약시간 숨김 |

웹은 OpenAI를 호출해 장소를 만들지 않는다. MCP는 ODsay 구현을 복제하지 않는다.

## 구조화된 복구 응답

웹의 내부 접근성 사전검사 API는 교체 가능한 장소 때문에 경로를 최종화할 수 없을 때 일반 오류 문자열 대신 내부 복구 계약을 반환한다. 최종 저장 API도 사전검사가 놓친 경로 차이를 위한 안전장치로 같은 문맥을 반환할 수 있다.

```ts
type PreviewStoreRepairResponse = {
  status: "repair_required";
  code:
    | "TRANSIT_PLACE_REPLACEMENT_REQUIRED"
    | "USER_PLACE_CONFIRMATION_REQUIRED";
  context: {
    traceId: string;
    dayIndex: number;
    routeId: "standard" | "carryme";
    segmentIndex: number;
    stopRef: string;
    placeConstraint: "fixed" | "replaceable";
    reason:
      | "destination_station_missing"
      | "walk_limit_exceeded"
      | "walk_path_missing";
  };
};
```

- 웹과 MCP 사이에서는 현재 의미 검증 실패 상태인 HTTP `422`를 유지할 수 있다.
- MCP는 `TRANSIT_PLACE_REPLACEMENT_REQUIRED`를 내부적으로 소비하고 최종 ChatGPT 응답에 422를 노출하지 않는다.
- `USER_PLACE_CONFIRMATION_REQUIRED`는 MCP의 `needs_clarification` 응답으로 변환한다.
- MCP는 `stopRef`로 자기 일정 안의 장소를 찾으므로 복구 응답에 장소명이나 좌표를 중복 전달하지 않는다.
- 공급자 원문 응답, 인증 정보와 사용자 출발지를 포함하지 않는다.

## 결정적인 실패 선택

동시에 실행한 경로 작업 중 먼저 끝난 오류를 복구 대상으로 선택하지 않는다. 같은 일차의 Standard·CarryME 작업은 현재 동시 실행 상한 안에서 한 묶음으로 완료하고, 그 묶음에서 발생한 도메인 실패를 다음 키로 정렬해 하나를 선택한다.

1. `dayIndex` 오름차순
2. `routeId`: Standard 우선, CarryME 후순위
3. `segmentIndex` 오름차순
4. `stopRef` 사전순

선택할 실패가 있으면 이후 일차 작업은 시작하지 않는다. 인증·계약·공유 캐시 설정처럼 장소 교체로 복구할 수 없는 운영 오류는 도메인 실패보다 우선해 요청 전체를 중단한다. 같은 입력과 같은 공급자 모의 응답은 실행 완료 순서와 무관하게 항상 같은 `stopRef`를 반환해야 한다.

## AI 장소 교체 흐름

1. MCP가 초안을 만들고 장소 좌표를 해석한다.
2. 대중교통 일정이면 인증된 웹 접근성 사전검사 API로 전체 Standard·CarryME 경로를 검사한다.
3. 웹은 구간별 공급자 성공 결과를 추적 ID 범위의 5분 공유 캐시에 저장하고, `replaceable` 장소의 접근 실패를 구조화해 반환한다.
4. MCP가 같은 `stopRef` 슬롯에 대해 지역 범위와 이미 실패한 후보를 제외한 AI 대체 장소를 만든다.
5. 네이버 장소 해석을 통과한 후보로 일정 초안을 갱신하고 접근성 사전검사를 다시 호출한다.
6. 대체 후보는 원래 실패한 장소와 별개로 최대 세 곳까지만 시도한다.
7. 성공한 후보는 기존 `stopRef`를 계승한다.
8. 세 후보가 모두 실패하면 해당 AI 장소를 경로에서 제거하고 원래 체류시간을 `자유시간` 타임라인으로 보존한 뒤 한 번 사전검사한다.
9. 제거 결과 하루의 방문 장소가 모두 없어지면 저장하지 않고 `needs_clarification`으로 여행 지역이나 필수 장소를 다시 요청한다.
10. 모든 경로가 허용 기준을 만족하면 MCP가 최종 저장 API를 한 번 호출하고, 웹은 캐시된 구간을 재사용해 원자적으로 저장한다.
11. 최종 저장에서 새 접근 실패가 발견되면 구조화된 422를 안전장치로 반환하되, 남은 전역 시간 예산이 없으면 추가 반복 호출하지 않는다.

## 고정 장소 흐름

- `fixed` 장소는 교체 응답을 만들지 않는다.
- 웹이 주변 정류장과 마지막 도보를 계산한다.
- 실제 또는 추정 도보 90분 이하면 같은 장소로 최종화한다.
- 90분 초과 또는 정류장을 찾지 못하면 `USER_PLACE_CONFIRMATION_REQUIRED`를 반환한다.
- MCP는 사용자의 확인 전까지 장소를 제거하거나 일정 링크를 만들지 않는다.

## 원자성과 멱등성

- 접근성 사전검사는 저장 상태를 변경하지 않는다.
- 최종 웹 저장 시도는 모든 일차와 Standard·CarryME 경로가 성공한 경우에만 한 번 수행한다.
- 실패 시 일부 경로나 수정 중간 상태를 미리보기 저장소에 기록하지 않는다.
- 모든 사전검사와 최종 저장은 같은 일정 ID와 추적 ID를 사용하되, 저장 버전은 최종 성공할 때만 증가한다.
- 이미 성공 저장된 동일 요청이 다시 도착하면 기존 멱등성 규칙을 사용해 중복 일정을 만들지 않는다.
- 한 요청에서 같은 `stopRef`와 같은 공급자 장소 참조를 다시 후보로 선택하지 않는다.

## 요청 추적 캐시

사전검사와 최종 저장 사이에서 변하지 않은 구간을 다시 호출하지 않도록 웹에 짧은 공유 캐시를 둔다.

- 키 구성: 추적 ID, 공급자, 이동수단, 정규화된 좌표 쌍의 해시
- 값: 성공한 공급자 구간 결과와 `durationSource`
- 권장 만료시간: 5분
- 실패 결과는 인증·계약 오류를 제외하고 장기 캐시하지 않는다.
- 캐시가 사라져도 경로 판정의 정확성은 유지되지만 60초 제한을 보장할 수 없으므로 운영 기능 활성화 조건에는 공유 캐시 설정을 포함한다.
- 원본 출발지 좌표를 로그나 사람이 읽을 수 있는 캐시 키에 넣지 않는다.

서버리스 인스턴스 메모리만으로 호출 간 적중을 보장할 수 없으므로 기존 Upstash Redis 경계를 사용한다. 로컬 테스트는 메모리 대체 저장소를 허용하되 운영에서 공유 캐시가 없으면 배포 모드를 `on`으로 활성화하지 않는다.

## 시간 및 호출 제한

- 한 AI 장소의 대체 후보는 최대 세 곳이다.
- 정류장 후보도 장소당 최대 세 곳이다.
- MCP 함수의 60초 제한보다 짧은 전역 시간 예산을 두고 사전검사와 최종 저장이 함께 공유한다.
- 개별 웹 경로 계산은 기존 40초 상한을 넘기지 않으며 전달받은 남은 예산이 더 작으면 그 값을 사용한다.
- 남은 시간이 다음 후보의 최소 호출 예산보다 작으면 즉시 중단하고 안정적인 시간 초과 오류를 반환한다.
- Standard와 CarryME에 동일한 좌표 구간이 있으면 같은 요청 추적 캐시를 공유한다.
- 시간 예산과 별도로 추적 ID당 실제 ODsay 요청 수에 강제 상한을 둔다. 캐시 적중은 호출 수에 포함하지 않고, 재시도·`pointSearch`·대중교통·도보 요청은 모두 포함한다.
- 사전검사와 최종 저장이 같은 상한을 공유하도록 Redis에서 `planme:route-provider-budget:{traceId}` 카운터를 원자적으로 증가시키고 5분 뒤 만료한다.
- 상한은 `PLANME_ODSAY_MAX_REQUESTS_PER_TRACE`로 주입한다. 임의 기본값을 두지 않고 대표 스모크 테스트의 최대 관측값과 여유분을 근거로 확정한다.
- 상한이 없거나 잘못됐으면 공개 기능을 활성화하지 않는다. 상한을 넘기기 직전 실제 공급자 호출을 차단하고 `PROVIDER_CALL_BUDGET_EXCEEDED`로 종료한다.
- Redis 호출 카운터를 읽거나 증가시키지 못하면 공급자를 미계측 상태로 호출하지 않고 `ROUTE_PROVIDER_CONFIGURATION_ERROR`로 닫힌 실패 처리한다.

## 로그와 개인정보

기존 경로 실패 로그에 다음 필드를 추가하거나 유지한다.

- `traceId`, 공급자, 내부 오류 코드
- 일차, 경로 종류, 구간 번호, `stopRef`
- `placeConstraint`
- AI 생성 장소인 경우에만 장소명과 목적지 좌표
- 후보 번호, 정류장 후보 수, 실제·추정 여부, 최종 처리 결과

사용자 출발지 이름·좌표는 남기지 않는다. 사용자 고정 장소는 장소명·좌표 대신 `stopRef`와 실패 유형을 기본 로그로 사용한다. 공급자 원문 응답과 키는 기록하지 않는다.

## 실패 상태

| 코드 | 의미 | MCP 처리 |
| --- | --- | --- |
| `TRANSIT_PLACE_REPLACEMENT_REQUIRED` | AI 장소가 접근 기준을 충족하지 못함 | 다음 AI 후보 적용 |
| `USER_PLACE_CONFIRMATION_REQUIRED` | 고정 장소가 90분 기준을 넘거나 정류장 없음 | `needs_clarification` |
| `NO_VISIT_PLACE_REMAINED` | 제거 후 하루 방문 장소 없음 | `needs_clarification` |
| `ROUTE_PROVIDER_CONFIGURATION_ERROR` | 인증·계약·환경 설정 오류 | 교체하지 않고 운영 오류 |
| `ROUTE_FINALIZATION_TIMEOUT` | 전체 시간 예산 초과 | 재시도 폭주 없이 실패 |
| `PROVIDER_CALL_BUDGET_EXCEEDED` | 추적 ID별 공급자 호출 상한 도달 | 추가 공급자 호출 없이 실패 |

## 검증 기준

1. AI 장소 접근 실패가 저장 전 사전검사의 구조화된 응답으로 MCP에 전달된다.
2. MCP가 최대 세 후보만 시도하고 실패 후보를 반복하지 않는다.
3. 사용자 고정 장소는 어떤 복구 흐름에서도 교체·제거되지 않는다.
4. 사전검사는 미리보기 데이터를 남기지 않고 최종 저장은 한 번만 성공 처리된다.
5. 동일 구간은 사전검사와 최종 저장 사이에서 공급자 호출을 반복하지 않는다.
6. 공급자 인증 오류는 장소 교체로 오인하지 않는다.
7. 동시 실패 완료 순서가 달라도 같은 `stopRef`가 선택된다.
8. 공급자 호출 상한에 도달하면 다음 요청을 보내기 전에 차단된다.

## 리스크

- 사전검사 요청을 여러 번 왕복하면 ChatGPT 도구 시간 초과 가능성이 커진다. 후보 상한과 MCP 전역 시간 예산이 먼저 적용돼야 한다.
- 공유 캐시는 운영 의존성을 늘리지만 현재 60초 플랫폼 제한 안에서 단일 최종 저장을 보장하기 위한 활성화 조건이다.
- 장소 제거 뒤 Standard·CarryME 참조를 함께 정리하지 않으면 고아 `stopRef`가 생길 수 있으므로 정규화 검증을 다시 실행한다.

# PlanME 대중교통 접근 불가 장소 복구 설계

## 문서 정보

- 한글 주제명: PlanME 대중교통 접근 불가 장소 복구
- Linear 이슈: 없음
- 선행 문서: [인터뷰 문서](../01_interview/index.md)
- 변경 범위: 대중교통 일정 생성, 경로 최종화, 저장 데이터와 기존 상세 화면 표시 계약
- 비변경 범위: 자동차 경로 계산, 별도 사용자 입력 UI, 운영 배포 절차

## 결론

대중교통 목적지 정류장이 없다는 ODsay 오류 코드 `4`를 전체 일정 실패로 처리하지 않는다. 사용자 고정 장소는 주변 정류장과 마지막 도보를 조합해 복구하고, AI 추천 장소는 허용 도보시간을 넘으면 같은 여행 지역 안에서 최대 세 후보까지 교체한다.

장소 생성 문맥은 MCP가 소유하고 ODsay 경로 판정은 웹이 소유한다. MCP는 최종 저장 전에 웹의 내부 대중교통 접근성 사전검사를 호출하고, 웹이 교체 가능한 장소의 실패를 구조화해 반환하면 같은 요청 안에서 후보를 교체한다. 성공한 공급자 구간은 짧은 공유 캐시에 보관한 뒤 최종 저장 API를 한 번 호출한다. 추정 이동시간이 포함된 일정도 허용 기준 안이면 `routeFinalized=true`로 저장하되 Standard·CarryME 절약시간은 노출하지 않는다.

## 확정 설계

1. 공개 일정 요청은 `destinationType`과 `mustVisitPlaces`로 여행 지역과 필수 방문지를 명시적으로 분리한다.
2. 저장 경로 정류장은 `stopRef`와 `placeConstraint`로 논리적 장소와 교체 가능 여부를 보존한다.
3. 오류 코드 `4`인 대중교통 구간만 주변 정류장 복구를 수행한다.
4. 정류장 후보는 최대 세 곳을 실제 경로로 평가하고, 대중교통과 마지막 도보의 합계가 가장 짧은 후보를 선택한다.
5. 도보 API 실패 시 `직선거리 × 1.5 / 시속 3.5km + 5분`으로 보수적으로 추정한다.
6. AI 추천 장소는 마지막 도보 30분 이하만 유지하고, 사용자 고정 장소는 90분 이하까지 자동 최종화한다.
7. 웹은 사전검사·고정 장소 복구·경로 판정을, MCP는 AI 장소 생성·교체·제거와 단일 최종 저장 호출을 담당한다.
8. AI 교체 후보 세 곳이 모두 실패하면 해당 장소를 제거하고 원래 체류시간을 자유시간으로 남긴다.
9. 계산된 구간 시간과 체류시간으로 이후 일정 시각을 순차 재계산한다.
10. 추정 구간이 하나라도 있으면 절약시간을 숨기고, 별도 실패 문구나 가짜 경로선은 표시하지 않는다.
11. 동시 실행 실패는 완료 순서가 아니라 일차·경로·구간·장소 참조 순서로 결정한다.
12. 추적 ID별 실제 ODsay 호출에 강제 상한을 두고, 배포는 `off → smoke → on` 모드로 단계적으로 활성화한다.

## 확인된 근거

- 현재 GPTs와 GPT 앱 요청은 `destination` 하나에 지역과 정확한 장소를 함께 받는다.
- 현재 필수 장소 처리기는 `destination`을 항상 필수 방문지로 적용한다.
- 초안의 `requiredPlaceKind`는 저장 `RouteStop` 변환 중 사라져 웹 경로 최종화 시 고정·교체 가능 여부를 구분할 수 없다.
- MCP는 AI 일정 생성과 네이버 장소 후보 해석을 담당하고, 웹 저장 API는 ODsay 경로 최종화와 원자적 저장을 담당한다.
- 현재 웹 ODsay 제공자는 700m 이하 대중교통 구간을 직선거리 기반으로 추정하고, 오류 코드 `4`는 복구하지 않는다.
- 현재 경로 최종화는 AI 시간표 배열의 바이트 단위 불변을 검증하므로 승인된 시간표 보정 요구와 충돌한다.

## 주요 리스크

| 리스크 | 영향 | 대응 |
| --- | --- | --- |
| ODsay 전용 도보 API 계약이 운영 계정에서 허용되지 않을 수 있음 | 실제 도보 경로 사용 불가 | 운영 계약을 먼저 확인하고 추정 경로를 기능 저하 대안으로 유지 |
| `pointSearch` 최대 반경이 공식 문서에 명확하지 않음 | 먼 정류장 탐색 범위가 환경마다 달라질 수 있음 | 실제 키로 지원 반경을 측정하고 설정값 상한으로 제한 |
| 사전검사와 장소 교체로 ODsay 호출량과 응답시간 증가 | MCP 60초 제한, ChatGPT 도구 시간 초과와 비용 증가 가능 | 후보·구간 상한, 5분 요청 추적 캐시, 전역 시간 예산, 추적 ID별 강제 호출 상한과 단일 최종 저장 호출 |
| 동시 경로 실패 완료 순서가 매번 달라짐 | 서로 다른 장소를 교체해 재현과 테스트가 어려움 | 일차·Standard 우선·구간·`stopRef`의 결정적 정렬 |
| 기존 일정에는 신규 참조 필드가 없음 | 잘못된 제목 추론 또는 시각 변경 위험 | 레거시 일정은 기존 시간표를 그대로 유지 |
| 추정시간을 실제 경로처럼 표시할 수 있음 | 사용자 오인 | 상태를 저장하고 절약시간·경로선을 숨김 |

## 설계 밖에서 확인할 항목

- ODsay 운영 계약과 `pointSearch` 최대 반경은 기능 활성화 전 외부 의존성 검증으로 남긴다.
- 장소 운영시간 데이터는 현재 계약에 없으므로 이번 최종화에서 검증하지 않는다.
- 직접 Vercel 배포는 사용하지 않으며, 구현 완료 후에도 PR 병합 기반 자동 배포 규칙을 따른다.

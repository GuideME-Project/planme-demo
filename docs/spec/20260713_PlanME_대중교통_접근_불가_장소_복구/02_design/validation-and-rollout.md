# 검증과 적용

## 목적

실패가 발생했던 실제 ChatGPT 표면에서 대중교통 일정 생성을 복구하고, 정상 동작하는 자동차 일정과 기존 저장 일정의 회귀를 막는다.

## 검증 원칙

- 공급자 모의 테스트와 실제 ODsay 호출을 분리한다.
- 자동 테스트가 실제 운영 계약을 증명한다고 간주하지 않는다.
- GPTs와 GPT 앱은 서로 다른 진입점이므로 각각 새 대화에서 검증한다.
- 웹 저장 성공뿐 아니라 저장된 경로 상태, 시간표, 절약시간 표시를 함께 확인한다.
- 자동차 경로에는 신규 대중교통 복구 코드가 실행되지 않는지 확인한다.

## 자동 테스트

### 요청·장소 계약

| 시나리오 | 기대 결과 |
| --- | --- |
| `남해` + `destinationType=region` | `남해`가 방문 정류장으로 삽입되지 않음 |
| `보리암` + `destinationType=place` | 보리암이 `fixed`로 저장됨 |
| 지역 + `mustVisitPlaces` | 필수 장소가 모두 `fixed`로 보존됨 |
| 레거시 요청 | `destination`을 기존처럼 필수 장소로 처리 |
| AI 장소 교체 | 같은 `stopRef`를 유지하고 `replaceable` 유지 |

### 정류장·도보 복구

| 시나리오 | 기대 결과 |
| --- | --- |
| 오류 코드 `4` + 유효 정류장 | 대중교통과 마지막 도보를 합쳐 성공 |
| 정류장 후보 세 곳 | 총 이동시간이 가장 짧은 후보 선택 |
| 도보 API 성공 | `durationSource=provider`, 실제 경로 사용 |
| 도보 API 오류 `411~414` | 승인된 공식으로 시간 추정, 경로선 없음 |
| AI 장소 도보 30분 초과 | 구조화된 교체 요청 |
| 고정 장소 도보 90분 이하 | 장소 유지, 최종화 성공 |
| 고정 장소 도보 90분 초과 | 사용자 확인 요청 |
| 공급자 인증 오류 | 장소 교체 없이 운영 오류 |

### 교체·원자성

- 원래 AI 장소와 별도로 대체 후보를 최대 세 곳만 시도한다.
- 실패 후보와 같은 공급자 장소를 다시 선택하지 않는다.
- 세 후보 실패 후 해당 AI 장소만 제거한다.
- 제거 뒤 방문 장소가 남으면 자유시간을 유지하고 저장한다.
- 제거 뒤 방문 장소가 없으면 `needs_clarification`으로 종료한다.
- 접근성 사전검사는 저장 버전을 만들지 않고 최종 저장 API는 한 번만 호출한다.
- 실패한 최종화는 일부 경로나 저장 버전을 남기지 않는다.
- 사전검사와 최종 저장의 동일 구간은 5분 공유 캐시를 재사용한다.
- Standard·CarryME 실패 응답 순서를 바꿔도 일차·경로·구간 정렬에 따라 같은 장소가 복구 대상으로 선택된다.
- 추적 ID별 공급자 호출 상한에 도달하면 다음 ODsay 요청 전에 `PROVIDER_CALL_BUDGET_EXCEEDED`로 중단된다.

### 시간표·표시

- 실제·추정 구간 시간을 이후 타임라인에 순차 반영한다.
- 제목·설명·순서는 유지한다.
- CarryME 짐 숙소 도착과 Standard 숙소 도착이 동기화된다.
- 날짜 경계를 넘으면 저장하지 않는다.
- 추정 구간이 있으면 `routeFinalized=true`를 허용하되 `savingStatus=hidden_estimated`다.
- 화면과 GPT 응답에서 절약시간을 생략하고 `0분 절약`으로 표시하지 않는다.
- 레거시 데이터의 시간표는 신규 참조가 없을 때 변경하지 않는다.

### 자동차 회귀

- `drive` 경로는 ODsay 정류장 검색과 도보 추정 함수를 호출하지 않는다.
- 네이버 자동차 구간 시간, 형상과 저장 상태가 기존 테스트 결과와 같다.
- 동탄호수공원에서 부산으로 가는 1박 2일 일정 상세 화면이 정상 표시된다.

## 기존 테스트 변경

| 테스트 | 변경 방향 |
| --- | --- |
| `apps/web/scripts/check-itinerary-finalization.ts` | 시간표 바이트 불변을 제목·순서 불변과 계산 시각 정확성 검증으로 교체 |
| `apps/web/e2e/itinerary-finalized-routes.spec.ts` | 저장 후 시간표 보정, 추정 상태, 절약시간 숨김 검증 추가 |
| `apps/web/e2e/gpt-itinerary-generation.spec.ts` | 신규 장소 의도 필드와 선택적 절약시간 응답 검증 |
| MCP·핵심 패키지 테스트 | 지역·고정 장소 분리, `stopRef` 유지, 최대 세 후보 교체 추가 |

## 실제 ODsay 기술 확인

기능 활성화 전에 운영과 같은 계약의 키로 제한된 확인을 수행한다.

1. `pointSearch` 반경을 단계적으로 늘려 허용 최대값과 오류 응답을 기록한다.
2. 남해독일마을·보리암처럼 접근 조건이 다른 목적지에서 정류장 후보가 반환되는지 확인한다.
3. `searchWalkPathV2`가 서버 호출 계약에서 허용되는지 확인한다.
4. 도보 성공·도로망 연결 실패·경로 없음 사례를 각각 한 번 이상 관측한다.
5. 실제 도보시간과 `직선거리 × 1.5 / 시속 3.5km + 5분` 추정값을 비교한다.
6. 예상 공급자 호출량과 응답시간이 MCP 전역 55초 후보 예산과 개별 웹 계산 40초 상한 안에 드는지 측정한다.

실제 키, 전체 요청 URL과 공급자 원문 응답은 문서나 로그에 남기지 않는다.

## 실제 ChatGPT 수락 테스트

### GPTs PlanME

- 맞춤형 GPT의 PlanME를 새 대화에서 호출한다.
- 기본 요청: `강동역 출발, 남해 1박 2일, 대중교통`
- 지역만 지정한 요청과 `남해독일마을`·`보리암`을 필수 장소로 지정한 요청을 각각 실행한다.

### GuideME-PlanME 앱

- 일반 ChatGPT 새 대화에서 GuideME-PlanME 앱을 호출한다.
- GPTs와 같은 두 대중교통 요청을 실행한다.

### 공통 확인

1. 사용자에게 422가 노출되지 않는다.
2. 지역이 임의 방문지로 삽입되지 않는다.
3. 사용자 지정 장소가 유지된다.
4. AI 장소 교체가 세 후보를 넘지 않는다.
5. 저장 링크가 열리고 허용된 일정은 `routeFinalized=true`다.
6. 실제 또는 추정 이동시간이 총시간과 이후 일정 시각에 반영된다.
7. 추정 구간이 있으면 절약시간과 가짜 경로선이 없다.
8. 로그에서 일차·경로·구간과 처리 결과를 확인할 수 있고 출발지는 없다.

### 자동차 회귀

- `동탄호수공원 출발, 부산 1박 2일, 자동차` 요청을 실행한다.
- 기존 네이버 자동차 경로와 상세 화면 동작이 유지되는지 확인한다.

## 적용 순서

배포 모드는 `PLANME_TRANSIT_ACCESS_RECOVERY_MODE` 하나로 통일한다.

| 모드 | 내부 사전검사 | GPTs·GPT 앱 공개 흐름 | 목적 |
| --- | --- | --- | --- |
| `off` | 차단 | 기존 흐름 | 기본 배포와 즉시 롤백 |
| `smoke` | 서명된 스모크 요청만 허용 | 기존 흐름 | 실제 ODsay 계약·반경·호출량 측정 |
| `on` | 허용 | 신규 복구 흐름 | 수락 테스트와 운영 활성화 |

1. 자료형과 저장 읽기 호환성을 `off` 모드로 배포한다.
2. 웹 접근성 사전검사 API, 5분 공유 캐시, 공급자 호출 카운터와 단일 최종 저장 흐름을 `off` 모드로 배포한다.
3. GPTs·GPT 앱 요청 스키마와 MCP 장소 정규화를 배포한다.
4. 별도 검증 배포가 확인되면 그 환경을 사용한다. 확인되지 않으면 공개 흐름은 기존 동작을 유지한 채 배포 모드만 `smoke`로 바꾸는 PR을 병합하고, 서명된 제한 스크립트로만 실제 ODsay를 검증한다.
5. 스모크 결과로 검색 반경과 `PLANME_ODSAY_MAX_REQUESTS_PER_TRACE` 값을 확정한다.
6. 맞춤형 GPT의 PlanME Action OpenAPI 스키마를 다시 가져온다.
7. 활성화 조건이 충족되면 `off` 원복 PR을 미리 준비하고, 별도 승인·PR로 MCP와 웹을 모두 `on`으로 배포한다.
8. 배포 직후 GPTs·GPT 앱 새 대화 수락 테스트와 자동차 회귀를 실행한다.
9. 첫 대표 요청의 오류율, 전역 처리시간, 호출 상한과 캐시 적중률을 확인한다.

모드 전환과 원복은 저장소의 비민감 배포 설정 변경 PR을 병합해 자동 배포한다. Vercel MCP 직접 배포나 대시보드의 즉시 환경 변경은 사용하지 않는다.

## 관측 항목

- 일정 생성 요청 수와 최종 성공률
- 오류 코드 `4` 발생 수
- 고정 장소 복구 성공·확인 요청 수
- AI 장소 교체 후보별 성공률과 제거 수
- 실제·추정 도보 구간 수
- ODsay 호출 수, 응답시간, 인증·계약 오류 수
- 추적 ID별 공급자 호출 카운터와 상한 차단 수
- MCP 전체 처리시간, 사전검사 시간, 최종 저장 시간과 예산 초과 수
- GPTs와 GPT 앱의 진입점별 성공률
- 자동차 경로 회귀 오류

## 중단 조건

- 공급자 인증·계약 오류가 반복됨
- 운영 공유 캐시를 사용할 수 없음
- MCP 60초 제한 안의 전역 처리 예산 초과가 증가함
- 공급자 호출 상한이 미설정이거나 대표 요청에서 반복적으로 초과됨
- 사용자 고정 장소가 교체·제거됨
- 추정 구간에 절약시간이나 가짜 경로선이 표시됨
- 자동차 요청에서 대중교통 복구가 실행됨

중단 시 `off` 모드로 되돌리고 기존 오류 처리로 복귀하며, 저장 자료형의 읽기 호환성은 유지한다.

## 리스크

- 실제 ChatGPT 대화는 모델이 공개 필드를 누락할 수 있으므로 스키마 예시와 도구 설명을 함께 검증해야 한다.
- 실제 ODsay 호출은 비용과 호출 제한에 영향을 줄 수 있으므로 제한된 사례와 호출 상한으로 수행한다.
- 배포 모드만 되돌리고 자료형을 제거하면 레거시 읽기가 깨질 수 있으므로 읽기 호환 코드는 유지한다.

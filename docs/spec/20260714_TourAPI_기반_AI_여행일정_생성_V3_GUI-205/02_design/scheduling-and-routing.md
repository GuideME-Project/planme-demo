# 일정 계산과 경로 보정

## 결론

최종 방문 시각과 이동시간은 AI가 아니라 서버 일정 계산기가 만든다.
AI 또는 결정적 배열기가 선택한 공통 장소 순서를 입력으로 받고, 체류시간·식사·숙소·자유시간을 배치한 뒤 실제 경로 제공자 결과를 반영해 Standard와 CarryME 시간표를 각각 완성한다.

경로 오류는 코드별로 재시도·예상 도보·장소 제외·전체 실패를 구분한다. 지도 경로가 없는 예상값을 실제 경로처럼 표시하지 않는다.

## 일정 계산 순서

```text
검증된 TripPlan
  -> 일차별 기본 시간창 생성
  -> 숙소·식사·자유시간 블록 삽입
  -> Standard·CarryME 정류점 파생
  -> 구간별 경로 계산
  -> 실제 이동시간으로 시간표 전파
  -> 종료시간 초과 장소를 다음 일차로 이동
  -> 불가능 장소 제외 후 단조롭게 재계산
  -> 두 변형과 절약시간 확정
```

AI가 반환한 방문 시각이나 체류시간은 입력으로 받지 않는다.

## 기본 시간 정책

| 구분 | 정책 |
| --- | --- |
| 첫날 | 출발지에서 목적지까지 실제 이동이 끝난 시각부터 목적지 일정을 시작 |
| 중간 날 | 고정 숙소에서 09:30 출발 |
| 마지막 날 | 고정 숙소에서 09:30 출발, 17:00 복귀 이동 시작 |
| 점심 | 12:00~14:00 범위에 60분 |
| 저녁 | 18:00~20:00 범위에 60분 |
| 숙소 | 전체 여행에서 TourAPI 숙소 하나, 마지막 날 외 매일 복귀 |
| 빈 시간 | 위치 없는 자유시간 또는 숙소 휴식 |

사용자에게 시간 선호를 질문하지 않는다. 실제 이동이 기본 시간창을 밀면 식사 시간창 안에서 뒤로 이동하고, 시간창을 지킬 수 없으면 위치 없는 일반 식사 이벤트로 단순화한다.

1일 일정은 첫날과 마지막 날 규칙을 모두 적용한다. 출발지에서 목적지까지 실제 이동이 끝난 뒤 목적지 일정을 시작하고 같은 날 17:00에 복귀 이동을 시작한다. 이 시간창 안에 숙소와 실제 방문 장소 하나를 포함한 유효 일정을 만들 수 없으면 장소를 발명하거나 기간을 바꾸지 않고 생성 실패로 처리한다.

## 체류시간 정책

초기 서버 기본값은 다음과 같이 둔다. 이 값은 AI 프롬프트가 아니라 정책 상수이며 구현 시 단위와 근거를 주석으로 남긴다.

| 콘텐츠 유형 | 기본 체류시간 |
| --- | ---: |
| 관광지 | 90분 |
| 문화시설 | 120분 |
| 행사·축제 | 120분 |
| 레포츠 | 120분 |
| 쇼핑 | 90분 |
| 음식점 | 60분 |

TourAPI의 상세 정보에 명시적인 이용시간이 있더라도 이를 체류시간으로 자동 해석하지 않는다. 향후 별도 정책이 승인되기 전까지 위 기본값을 사용한다.

## 장소 부족과 시간 초과

- 같은 `contentId`를 일정 채우기용으로 반복하지 않는다.
- 일수보다 장소가 적으면 요청 기간을 유지하고 자유시간·숙소 휴식을 넣는다.
- 경로 계산 후 해당 일차의 종료시간을 넘는 마지막 방문지는 다음 일차로 이동한다.
- 다음 일차도 수용하지 못하면 자유시간으로 남기고 해당 장소는 일정에서 제외한다.
- 장소 제외 집합은 단조롭게 증가하며 같은 장소를 한 생성에서 다시 넣지 않는다.
- 숙소 또는 전체 여행의 마지막 실제 방문 장소까지 잃으면 생성 실패다.

## Standard와 CarryME 계산

### Standard

- 여행자가 수하물을 직접 운반하는 기준 경로다.
- 첫날 목적지 도착 뒤 필요한 숙소 체크인 경유를 포함한다.
- 마지막 날 외에는 해당 일차 마지막에 숙소 복귀를 포함한다.
- 수하물 관련 시간은 여행자 이동시간에 포함된다.

### CarryME

- 여행자는 불필요한 숙소 경유 없이 첫 방문 장소로 이동한다.
- 수하물 인계·배송·숙소 도착은 여행자 방문 장소와 분리된 수하물 이벤트와 경로로 계산한다.
- 관광 방문 순서와 숙소는 Standard와 같은 `TripPlan`을 참조한다.
- CarryME 시간표도 실제 여행자 이동시간을 기준으로 서버가 만든다.

절약시간은 같은 revision에서 `Standard 여행자 이동 완료시간 - CarryME 여행자 이동 완료시간`으로 계산하며 음수면 0으로 정규화한다. AI가 제안한 절약 문구나 예상값은 저장하지 않는다.

## 경로 구간 계약

```ts
type RouteSegment = {
  fromRef: string;
  toRef: string;
  mode: "drive" | "transit" | "walk";
  source: "naver" | "odsay" | "estimated_walk";
  distanceMeters: number;
  durationSeconds: number;
  geometryStatus: "complete" | "partial" | "unavailable";
  paths: Array<Array<{ lat: number; lng: number }>>;
  providerCode?: string;
};
```

- `estimated_walk`는 `paths=[]`, `geometryStatus="unavailable"`이다.
- 제공자 원본 오류 메시지와 요청 URL을 저장 응답에 포함하지 않는다.
- 정류점은 경로 기준점 또는 `contentId`로 참조하고 브라우저가 보낸 좌표를 신뢰하지 않는다.

## 자동차 경로

네이버 Directions를 서버에서만 호출한다.

- 좌표가 있는 두 정류점 이상만 요청한다.
- 네트워크, 408, 429, 5xx는 해당 구간을 한 번 재시도한다.
- 인증·설정 누락, 입력 오류와 지도 형상 누락은 재시도하지 않는다.
- 필수 출발지·목적지·숙소 구간 실패는 전체 생성 실패다.
- 선택 방문 장소만 실패하면 해당 장소를 제외하고 공통 계획부터 다시 계산한다.

## ODsay 대중교통과 도보 보정

### 근거리 `-98`

1. 대중교통 경로가 `-98`을 반환한다.
2. 두 장소의 직선거리를 계산한다.
3. 700m 이하이면 ODsay 도보 경로를 시도한다.
4. 도보 경로가 성공하면 실제 도보 구간을 저장한다.
5. 도보가 411~414로 실패하면 `estimated_walk`를 저장한다.
6. 700m를 초과하면 예상 도보를 만들지 않고 경로 불가 정책을 적용한다.

`estimated_walk` 시간은 다음과 같다.

```text
durationMinutes = max(1, ceil(straightDistanceMeters / 4000 * 60))
```

시속 4km, 분 단위 올림이며 700m 이하에서만 허용한다.

### 오류 처리 행렬

| 오류 | 분류 | 재시도 | 처리 |
| --- | --- | ---: | --- |
| `-98` | 근거리 대중교통 없음 가능성 | 아니요 | 700m 이하 도보 보정 |
| 411~414 | 도보 링크·결과 없음 | 아니요 | 700m 이하 `estimated_walk` |
| 3·4·5 | 정류장 탐색 불가 계열 | 아니요 | 선택 장소 제외, 필수 기준점이면 실패 |
| 6 | 서비스 지역 밖 | 아니요 | 선택 장소 제외, 필수 기준점이면 실패 |
| `-99` | 경로 없음 | 아니요 | 선택 장소 제외, 필수 기준점이면 실패 |
| `-8`·`-9` | 입력 오류 | 아니요 | 생성 실패 및 내부 계약 오류 기록 |
| 408·429·5xx·`-1` | 일시 오류 | 1회 | 같은 구간만 제한 재시도 |
| 인증 실패 | 설정 오류 | 아니요 | 전체 생성 실패 |
| 문서화되지 않은 코드 | 미분류 | 아니요 | 실패 폐쇄, 성공 데이터 생성 금지 |

구현 전 ODsay 공식 문서·승인된 샘플로 3·4·5·6·`-8`·`-9`·`-99`의 현재 의미를 재검증한다. 코드 의미가 문서와 다르면 분류 이름을 고치되 사용자와 확정한 처리 원칙은 유지한다.

## 재계산과 실패 경계

- 선택 장소 하나가 경로 불가이면 그 장소만 제외하고 `TripPlan`부터 다시 계산한다.
- 이미 제외한 장소를 AI에 다시 보내거나 대체 검색하지 않는다.
- 경로 재계산은 남은 장소 수만큼만 가능하므로 무한 루프가 없다.
- 필수 숙소, 출발지 또는 목적지 기준점 경로 실패는 즉시 terminal `failed`다.
- 편집 중 실패하면 `pending`을 폐기하고 이전 `active`를 유지한다.
- 새 생성 실패는 사용할 수 있는 일정 링크를 반환하지 않는다.

## 브라우저 경계

- 브라우저는 ODsay와 네이버 Directions를 직접 호출하지 않는다.
- `NEXT_PUBLIC_ODSAY_API_KEY`에 의존하는 브라우저 코드와 브라우저 ODsay 캐시는 제거한다.
- 웹은 서버가 저장한 경로 구간과 시간표만 렌더링한다.
- 편집 중 임시 지도선·임시 이동시간을 계산하지 않고 기존 `active`와 `pending` 상태를 표시한다.
- 경로선이 없는 `estimated_walk`는 점선으로 추정선을 만들지 않고 텍스트 상태만 표시한다.

## 관측성

구간 로그에는 다음만 남긴다.

- 작업 ID, revision, day, variant, segment index
- provider, 안정된 provider code, attempt
- duration, distance, geometry status
- `estimated_walk` 여부와 직선거리
- 장소 제외 결과와 내부 reason code

API 키, 전체 URL, 원본 주소, 제공자 원본 응답은 로그에 남기지 않는다.

## 리스크

- 직선거리 기반 예상 도보는 강·철도·출입구 같은 장애물을 반영하지 못한다. 700m 상한, 보수적 속도, 경로선 미표시와 예상 상태로 완화한다.
- 기본 체류시간이 장소 특성과 다를 수 있다. AI가 임의 시간을 만들게 하지 않고 정책 상수와 회귀 테스트로 통제한다.
- 장소 제외가 일정 품질을 낮출 수 있다. 장소 발명보다 축소·자유시간을 우선한다.
- Standard와 CarryME 계산량이 크다. 비동기 routing 단계를 일차·변형 단위로 나눠 서버리스 제한을 넘지 않게 한다.

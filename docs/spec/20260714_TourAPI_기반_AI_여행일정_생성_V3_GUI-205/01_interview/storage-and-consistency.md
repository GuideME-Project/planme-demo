# 저장과 정합성 정책

## 목적

- 이 주제를 확인하는 이유: 생성·수정 실패가 사용자가 보고 있는 정상 일정을 덮어쓰지 않도록 저장 경계와 ID 정책을 정한다.
- 이 주제가 불명확하면 생기는 리스크: 부분 계산 결과가 활성 일정이 되거나 같은 입력의 새 생성이 기존 공유 링크를 덮어쓸 수 있다.

## Questions

1. 기존 Redis를 재사용하는가?
2. 일정 수정 중 실패하면 어떤 버전을 유지하는가?
3. TourAPI 후보 캐시의 보존기간과 장애 시 정책은 무엇인가?
4. 새 생성, 재시도, 편집의 일정 ID와 revision 정책은 무엇인가?
5. TourAPI 일부 콘텐츠 유형만 실패하면 마지막 정상 캐시를 어떤 단위로 사용하는가?

## Answers

1. 현재 Upstash Redis 저장소를 재사용한다.
2. 수정은 같은 일정 ID에 `pending` revision을 만들고 모든 파생 계산이 성공하면 원자적으로 `active`로 전환한다. 실패하면 `pending`을 폐기하고 기존 `active`를 유지한다. 직전 정상본은 `previous` 하나만 유지한다.
3. TourAPI 후보는 별도 키 공간에 정상 TTL 24시간으로 저장한다. TourAPI 장애 시 마지막 정상 데이터를 최대 7일까지 사용할 수 있고, 그 이후 또는 캐시가 없으면 생성에 실패한다. 오래된 캐시 사용 사실은 기록한다.
4. 새 생성은 입력이 같아도 새 일정 ID를 만든다. 같은 도구 요청의 재시도만 멱등성 키로 같은 결과를 반환한다. 편집은 같은 일정 ID에서 새 revision을 만든다.
5. 콘텐츠 유형별로 독립 적용한다. 정상 응답은 최신 결과를 사용하고 네트워크·429·5xx 등 장애가 난 유형만 최대 7일의 마지막 정상 캐시를 사용한다. 정상 응답이 0개이면 캐시를 되살리지 않는다.

## Score

- 현재 불명확성 점수: `0.15`
- 목표 임계값: `Standard 0.20`
- 점수 근거: 저장소, 스냅샷, TTL, ID와 멱등성의 제품 정책이 확정됐다.
- 다음에 낮춰야 할 불확실성: Redis 키 형식, Lua 원자 연산, 잠금·멱등성 TTL과 정리 정책을 설계한다.

## Confirmed

- 최종 일정 TTL은 현재 기본값인 7일을 유지한다.
- TourAPI 후보 캐시는 최종 일정과 다른 키 이름 공간을 사용한다.
- 모든 파생 결과는 계산을 시작한 정확한 `pending` revision을 참조해야 한다.
- 웹 편집 결과의 두 경로와 시간표도 같은 `pending` revision을 참조하고 한 번에 활성화한다.
- 각 revision은 계산에 사용한 TourAPI 최소 정규화 장소 스냅샷을 내장한다.
- 장소 표시는 후보 캐시나 TourAPI 재조회 결과가 아니라 저장된 revision 스냅샷을 기준으로 한다.
- 각 장소 스냅샷에 조회 시각과 오래된 캐시 사용 여부를 기록한다.
- 장애 유형에 캐시가 없으면 숙소는 생성 실패, 음식점은 위치 없는 식사 시간, 방문 장소는 남은 유형으로 축소 생성한다.
- 완전한 장기 버전 이력과 사용자용 버전 UI는 범위에서 제외한다.
- 기존 V1/V2 키는 적극적으로 삭제하지 않고 기존 TTL 만료에 맡긴다.
- 기존 V1/V2 일정의 V3 마이그레이션은 하지 않는다.

# 채널 계약과 사용자 노출

## 목적

- 이 주제를 확인하는 이유: GPTs Actions, GPT App MCP와 웹이 같은 생성 결과를 사용하되 채널별 안내 범위를 명확히 한다.
- 이 주제가 불명확하면 생기는 리스크: 채널마다 다른 질문과 장소 검증이 실행되거나, 웹 상세에 불필요한 내부 제외 안내가 노출될 수 있다.

## Questions

1. GPTs Actions와 GPT App MCP는 같은 생성 로직을 사용하는가?
2. 사용자가 요청한 특정 장소가 TourAPI에 없으면 어떻게 표시하는가?
3. 기존 일정이 없어도 일정 생성을 진행할 수 있는가?
4. 시간이 오래 걸리는 일정 생성 결과를 각 ChatGPT 채널에서 어떻게 받는가?

## Answers

1. 두 어댑터가 하나의 서버 일정 오케스트레이터와 공통 요청·응답 계약을 사용한다. 어댑터는 입력 전달과 채널별 출력 형식 변환만 담당한다.
2. 해당 장소는 일정에서 제외하고 나머지 후보로 생성한다. 제외 안내는 ChatGPT 대화 결과와 GPT App 위젯에 표시하고 웹 상세 화면에는 표시하지 않는다. 제외 이유는 Redis에 저장한다.
3. 기존 일정이 없어도 새 일정을 생성할 수 있다.
4. 생성 시작과 결과 조회를 분리한다. GPTs와 GPT App은 작업 상태를 자동 조회하고 완료된 결과를 대화 또는 위젯에 표시한다.

## Score

- 현재 불명확성 점수: `0.10`
- 목표 임계값: `Standard 0.20`
- 점수 근거: 공통 오케스트레이터, 채널별 역할과 제외 안내 범위가 확정됐다.
- 다음에 낮춰야 할 불확실성: 공통 응답 DTO와 위젯 표시 필드를 설계 단계에서 고정한다.

## Confirmed

- ChatGPT에서 보이는 결과는 GPTs 최종 응답과 GPT App 위젯을 포함한다.
- 웹 상세 화면에는 TourAPI 미일치 장소 제외 안내를 추가하지 않는다.
- GPTs와 GPT App이 서로 다른 모델 프롬프트나 장소 검증 정책을 가지지 않는다.
- 사용자에게 허용된 네 입력 외의 추가 질문은 어느 채널에서도 하지 않는다.
- 장소 후보 일부가 제외돼도 남은 후보가 있으면 축소된 일정을 반환한다.
- 비동기 상태 조회를 위해 사용자에게 다시 입력하거나 확인하도록 요구하지 않는다.
- 웹은 경로를 직접 계산하지 않고 서버가 활성화한 일정 revision만 표시한다.
- 웹 편집 계산 중에는 기존 `active` 일정을 유지하면서 `pending` 상태를 별도로 표시한다.

# 제품 범위와 사용자 질문 정책

## 목적

- 이 주제를 확인하는 이유: 일정 생성의 최우선 목표와 사용자에게 요구할 수 있는 입력 범위를 고정한다.
- 이 주제가 불명확하면 생기는 리스크: 장애나 후보 부족을 사용자 추가 질문으로 떠넘기거나, 기존 일정을 억지로 호환하면서 새 회귀가 생길 수 있다.

## Questions

1. 이번 변경의 최우선 목표는 무엇인가?
2. 일정 생성을 위해 사용자에게 어떤 값을 물을 수 있는가?
3. 사용자가 자발적으로 제공한 추가 정보는 사용할 수 있는가?
4. 여행 중 숙소 변경과 기존 일정 호환을 이번 범위에 포함하는가?

## Answers

1. 기능 확장보다 회귀 방지가 최우선이다.
2. 출발지, 목적지, 이동 수단, 여행 기간만 능동적으로 질문한다. 이미 받은 값은 다시 묻지 않는다.
3. 자발적으로 받은 선호, 특정 장소, 여행 날짜는 검증 후 사용할 수 있지만 먼저 질문하지 않는다.
4. 첫 버전에서는 한 숙소를 전체 여행에 사용한다. 기존 V1/V2 일정과 링크의 호환·마이그레이션은 필요하지 않다.

## Score

- 현재 불명확성 점수: `0.05`
- 목표 임계값: `Standard 0.20`
- 점수 근거: 목표, 허용 질문, 선택 정보, 비목표와 필수 회귀 검증 기준이 확정됐다.
- 다음에 낮춰야 할 불확실성: 설계 단계에서 네 입력값의 DTO 필수·선택 조건과 채널별 수집 상태를 구체화한다.

## Confirmed

- 장소 후보가 부족해도 추가 취향이나 장소를 질문하지 않는다.
- 일부 TourAPI 후보만 있으면 축소된 일정을 자동 생성한다.
- TourAPI 숙소 후보 또는 실제 방문 장소 후보가 전혀 없으면 장소를 발명하지 않고 생성 실패로 처리한다.
- 선호는 TourAPI 후보의 순위 조정에만 사용한다.
- 사용자가 특정 장소를 말해도 TourAPI에서 일치한 장소만 일정에 포함한다.
- 출발지·목적지 경로 기준점의 좌표 확인이 실패한 경우에만 같은 항목을 다시 질문한다.
- 날짜를 제공한 경우에만 실제 여행 날짜에 유효한 행사·축제를 후보로 사용할 수 있다.
- 여러 숙소를 옮기는 일정은 후속 범위다.
- 장소 후보가 부족해도 요청한 여행 기간은 줄이지 않는다.
- 위치 없는 자유시간·숙소 휴식은 허용하지만 TourAPI 장소 중복이나 신규 장소 생성으로 빈 시간을 채우지 않는다.

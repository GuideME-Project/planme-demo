# PlanME 일정 생성 완료 기준

## 목적

이 문서는 PlanME 일정 생성과 상세 화면의 경로 재계산을 "한 번 화면에 표시됨"이 아니라, GPTs와 ChatGPT 앱에서 반복해서 사용할 수 있는 상태로 완료 판정하기 위한 기준을 정의한다.

다음과 같은 결과는 생성 응답이나 상세 화면이 표시되더라도 완료로 인정하지 않는다.

- 내부 장소 검색 오류를 사용자 입력 부족으로 안내한다.
- 장거리 짐 배송이 출발 직후 도착한 것으로 표시된다.
- 숙박일의 CarryME 일정이 관광지에서 끝나고 숙소로 복귀하지 않는다.
- Standard와 CarryME의 시작점 또는 종료점이 다른데 절약시간을 비교한다.
- GPTs, 앱 위젯, 상세 화면이 서로 다른 일정이나 시간을 표시한다.
- 같은 프롬프트가 성공과 실패를 반복한다.

## 적용 범위

- Custom GPT Actions를 사용하는 GPTs
- GuideME ChatGPT 앱의 PlanME 도구
- 일정 생성 서버와 장소 검색
- 자동차 및 대중교통 경로 최종화
- ChatGPT 위젯
- PlanME 상세 일정 화면과 지도
- 생성 일정 저장 및 공유 링크
- 운영 로그와 오류 메시지

## 1. 입력 계약

### 완료 기준

- 일정 생성에는 다음 네 항목이 필요하다.
  - 출발지
  - 목적 지역 또는 목적 장소
  - 여행 기간
  - 이동 수단
- 사용자가 출발지, 목적 지역, 여행 기간을 제공하고 이동 수단만 생략한 경우 AI는 이동 수단만 한 번 질문한다.
- 사용자가 후속 답변으로 `자동차` 또는 `대중교통`을 선택하면 최초 프롬프트의 출발지, 목적지, 기간을 이어받아 일정을 생성한다.
- 이동 수단을 답한 뒤 같은 질문을 반복하거나 최초 프롬프트의 조건을 다시 요구하지 않는다.
- 이동 수단을 묻기 전에 자동차 또는 대중교통을 임의로 선택하지 않는다.
- 사용자가 지역만 지정한 경우 AI가 해당 지역의 방문 장소와 숙소 후보를 정해 일정을 생성할 수 있어야 한다.
- 사용자가 특정 장소를 지정한 경우 해당 장소는 고정하고, 고정하지 않은 중간 방문지는 AI가 조정할 수 있어야 한다.
- 숙소, 여행 취향, 인원, 짐 개수는 사용자가 생략할 수 있으며 일정 생성의 필수 입력으로 취급하지 않는다.
- 필요한 네 항목이 갖춰지면 동일 정보를 더 구체적으로 다시 입력하라고 요구하지 않는다.
- 장소 검색, AI 호출, 경로 계산 같은 내부 오류를 사용자 입력 부족으로 표현하지 않는다.
- 자동차와 대중교통 분기 테스트는 각각 독립된 새 대화에서 같은 첫 프롬프트로 시작한다.
- 이전 대화에서 선택한 이동 수단을 다음 테스트에 재사용하지 않는다.

### 실패 예시

- `동탄호수공원에서 남해 1박 2일 여행`, `자동차`까지 입력했는데 "남해 핵심 명소 위주로 다시 시도"하라고 안내한다.
- 사용자가 목적 지역을 말했는데 상세 주소나 구체적인 관광지를 추가로 요구한다.

## 2. 날짜와 여행 구조

### 완료 기준

- 생성된 일차 수는 사용자가 요청한 여행 기간과 일치한다.
- 각 날짜의 타임라인은 시간순이며 같은 날짜 안에서 시간이 역행하지 않는다.
- 이동, 체류, 식사, 체크인, 복귀 시간이 서로 겹치거나 물리적으로 불가능하지 않아야 한다.
- 숙박이 남아 있는 날은 Standard와 CarryME 모두 해당 날짜의 동일한 숙소에서 종료한다.
- 다음 날은 직전 날짜에 종료한 숙소에서 시작한다.
- 여행 마지막 날은 Standard와 CarryME 모두 최초 프롬프트의 출발지로 복귀해 종료한다.
- 마지막 날에는 숙소 복귀나 추가 숙박 이벤트를 넣지 않는다.
- 사용자가 최종 복귀지를 별도로 지정한 경우에만 최초 출발지 대신 지정한 복귀지를 사용한다.
- 연속된 날짜 사이의 시작 위치는 직전 날짜의 종료 위치와 동일한 장소 참조를 사용해야 한다.
- 같은 숙소에서 연박하면 날짜 사이에 불필요한 숙소 간 이동이나 중복 짐 배송을 만들지 않는다.

## 3. Standard와 CarryME 동선 계약

### Standard

- 출발지에서 짐을 직접 가지고 이동한다.
- 첫 숙박일에는 관광 전에 숙소를 방문해 짐을 놓거나 체크인하는 동선을 포함한다.
- 관광 후 숙박하는 날에는 해당 숙소로 복귀한다.
- 마지막 날에는 숙소에서 짐을 가지고 출발해 관광 후 최초 출발지 또는 사용자가 지정한 복귀지로 돌아온다.

### CarryME

- 여행자 동선에서 관광 전 숙소 방문을 제거한다.
- 짐 배송은 여행자의 행선지가 아닌 별도 타임라인 이벤트로만 표시한다.
- 여행자는 출발지에서 첫 관광지 또는 사용자 목적지로 바로 이동한다.
- 관광 후 숙박하는 날에는 Standard와 동일한 숙소로 복귀한다.
- 마지막 날에는 숙소에서 짐을 맡긴 뒤 여행자는 관광하고 최초 출발지 또는 사용자가 지정한 복귀지로 돌아온다.

### 공통 완료 기준

- 같은 날짜의 Standard와 CarryME는 동일한 출발점과 최종 도착점을 가져야 한다.
- 두 동선의 차이는 짐을 놓기 위한 중간 숙소 방문 여부여야 한다.
- 짐 배송용 숙소를 CarryME 여행자 경로의 중간 정차지로 계산하지 않는다.
- 마지막 날의 짐 배송 목적지를 CarryME 여행자 경로의 중간 정차지로 계산하지 않는다.
- 동일 장소의 배송 이벤트와 여행자 방문 이벤트 때문에 0거리 또는 중복 이동 구간을 만들지 않는다.
- 경로 요약, 타임라인, 지도 선, 행선지 편집 목록이 동일한 동선을 표현해야 한다.

## 4. 짐 배송 목적지와 시간

### 완료 기준

- 짐 배송 이벤트는 실제 숙소, 최초 출발지 또는 사용자가 지정한 수령 지점에 연결된 장소 참조를 가진다.
- 숙박이 남아 있는 날의 짐 배송 목적지는 해당 날짜의 실제 숙소다.
- 마지막 날의 짐 배송 목적지는 사용자가 별도 수령지를 지정하지 않은 경우 최초 출발지다.
- 사용자가 출발지를 `집`이라고 말하지 않았다면 화면에서 최초 출발지를 임의로 `집`이라고 표현하지 않는다.
- 숙박일의 짐 도착 시각은 짐의 출발 또는 접수 시각보다 늦고, CarryME 여행자의 숙소 도착 시각보다 빠르거나 같아야 한다.
- 마지막 날의 짐 도착 시각은 숙소에서의 출발 또는 접수 시각보다 늦고, CarryME 여행자의 최초 출발지 도착 시각보다 빠르거나 같아야 한다.
- 짐은 여행자보다 목적지에 먼저 도착할 수 있지만 실제 이동 거리와 배송 방식으로 가능한 시간이어야 한다.
- 짐 배송 이벤트의 시각을 출발 이벤트의 체류시간만 더해 계산하지 않는다.
- 장거리 이동에서 출발 직후 10분 또는 15분 만에 목적 지역 숙소에 도착한 것으로 표시하지 않는다.
- 배송 이벤트를 경로 시간 보정에서 제외하더라도 타임라인의 시간순 정합성은 유지한다.
- GPTs 위젯, 앱 위젯, 상세 화면, 저장 데이터는 동일한 짐 목적지와 도착 시각을 표시한다.

### 실패 예시

- 동탄호수공원에서 08:00 출발한 짐이 남해 숙소에 08:10 도착한다.
- 마지막 날의 짐 배송 목적지가 최초 출발지가 아니라 전날 숙소로 남아 있다.
- 사용자가 마포구청을 출발지로 입력했는데 마지막 날 짐 목적지를 `집`으로 표시한다.

## 5. 이동시간과 절약시간

### 완료 기준

- 이동시간은 선택한 이동 수단에 맞는 경로 계산 결과를 사용한다.
- 자동차 일정에 대중교통 경로를 사용하거나 대중교통 일정에 자동차 경로를 사용하지 않는다.
- Standard와 CarryME의 시작점, 종료점, 비교 날짜가 모두 같을 때만 절약시간을 계산한다.
- 절약시간은 두 동선의 실제 이동시간 차이로 계산한다.
- 경로 일부가 추정값이거나 계산에 실패한 경우 절약시간을 숨긴다.
- 절약시간이 0이면 숫자를 과장하지 않고 `시간 절약 없음`으로 표시한다.
- 절약시간이 없어도 CarryME의 짐 없는 이동 가치는 별도 문구로 표현할 수 있다.
- 경로가 서로 다른 목적지에서 끝나는 상태에서 절약시간을 노출하지 않는다.

## 6. 장소와 경로 확정

### 완료 기준

- 화면에 노출하는 모든 행선지는 장소명과 좌표가 확정되어야 한다.
- 사용자 출발지와 사용자가 지정한 목적 장소는 임의의 다른 장소로 교체하지 않는다.
- AI가 추천한 중간 장소가 경로 계산에 부적합하면 같은 목적 지역 안의 대안 장소로 교체하거나 제외할 수 있다.
- 대중교통 일정은 정류장 접근, 도보 연결, 경로 존재 여부를 확인한다.
- 자동차 일정은 모든 대표 구간의 자동차 경로가 계산되어야 한다.
- 경로 계산이 완료되기 전에 최종 일정 링크를 성공으로 반환하지 않는다.
- 저장된 일정의 경로, 시간표, 절약시간은 하나의 최종화 결과로 원자적으로 반영한다.

## 7. 저장과 화면 일치

### 완료 기준

- GPTs와 앱은 같은 서버 계약을 사용한다.
- 성공 응답에는 유효한 일정 ID와 상세 링크가 포함된다.
- ChatGPT 위젯의 일정과 상세 링크의 일정이 동일해야 한다.
- 상세 링크를 열면 생성 당시의 일정이 그대로 다시 표시되어야 한다.
- 이후 다른 일정을 생성해도 기존 일정 ID의 내용이 덮어써지지 않는다.
- 위젯, 상세 화면, OpenGraph 미리보기는 제목, 기간, 동선, 시간, 절약시간에서 모순되지 않아야 한다.
- 상세 지도를 클릭하거나 이동한 뒤에도 지도 타일이 빈 칸으로 남지 않아야 한다.

## 8. 오류 처리와 관측성

### 완료 기준

- 오류는 최소한 다음 단계로 구분해 기록한다.
  - 입력 해석
  - AI 일정 생성
  - 장소 검색 및 좌표 확정
  - 경로 계산
  - 일정 최종화
  - 저장
  - GPTs 또는 앱 응답 전달
- GPTs와 앱 요청에는 같은 요청 흐름을 추적할 수 있는 식별자가 있어야 한다.
- 운영 로그에는 실패 단계, 내부 오류 코드, 구간 번호, AI가 생성한 장소명과 좌표를 남길 수 있다.
- 사용자 출발지의 장소명과 좌표는 운영 로그의 장소 상세에서 제외한다.
- 재시도 가능한 내부 오류와 사용자 입력이 필요한 오류를 구분한다.
- 내부 오류가 발생하면 사용자가 목적지를 더 자세히 말해야 한다는 메시지 대신, 재시도 가능 여부와 실패 단계를 정확히 안내한다.

## 9. 회귀 검증 시나리오

### 고정 첫 프롬프트

다음 문자열을 GPTs와 ChatGPT 앱에서 그대로 사용한다.

1. `동탄에서 부산 1박2일 여행`
2. `마포구청에서 남해 1박 2일 여행`
3. `강동역에서 양양 2박3일 여행`

`동탄`처럼 범위가 넓은 출발지도 유효한 입력으로 취급하며 더 정확한 장소명이나 주소를 사용자에게 다시 묻지 않는다. 서버가 확정한 대표 장소명과 좌표를 화면에서 확인할 수 있어야 하며 마지막 날에도 동일한 장소 참조로 복귀해야 한다. `마포구청`과 `강동역`처럼 특정 장소를 지정한 경우 동명의 다른 장소나 인접 역으로 조용히 변경하지 않는다.

### 이동 수단 분기

각 첫 프롬프트마다 다음 두 분기를 독립된 새 대화에서 실행한다.

| 분기 | 최초 이동 수단 답변 | 상세 화면 재계산 |
|---|---|---|
| A | 자동차 | 대중교통으로 변경 후 재계산 |
| B | 대중교통 | 자동차로 변경 후 재계산 |

### 대화 단계

1. 이동 수단을 제외한 고정 첫 프롬프트를 입력한다.
2. AI가 자동차와 대중교통 중 어떤 방식인지 한 번만 질문하는지 확인한다.
3. A 분기는 `자동차`, B 분기는 `대중교통`으로 답한다.
4. AI가 출발지, 목적지, 기간을 다시 묻지 않고 일정을 생성하는지 확인한다.
5. 생성 응답의 상세 일정 버튼 또는 일정 링크를 클릭한다.
6. 같은 일정 ID의 PlanME 데모 상세 화면이 열리는지 확인한다.
7. 제목, 기간, 출발지, 이동 수단, 일차별 시간표, 짐 이벤트를 확인한다.
8. 상세 화면에서 현재 이동 수단의 반대 수단을 선택한다.
9. `경로 다시 계산` 버튼을 누른다.
10. 재계산 결과와 저장 상태를 확인한다.

### 일차별 위치 계약

#### 1박 2일

- 1일 차: 최초 출발지에서 시작해 목적 지역을 여행하고 숙소에서 종료한다.
- 2일 차: 1일 차 숙소에서 시작해 목적 지역을 여행하고 최초 출발지에서 종료한다.

#### 2박 3일

- 1일 차: 최초 출발지에서 시작해 목적 지역을 여행하고 1일 차 숙소에서 종료한다.
- 2일 차: 1일 차 숙소에서 시작해 목적 지역을 여행하고 2일 차 숙소에서 종료한다.
- 3일 차: 2일 차 숙소에서 시작해 목적 지역을 여행하고 최초 출발지에서 종료한다.
- 같은 숙소에서 연박하면 1일 차와 2일 차 숙소는 동일한 장소 참조를 사용한다.
- 숙소가 바뀌면 2일 차 시작 숙소와 종료 숙소를 구분하고, 3일 차는 2일 차 종료 숙소에서 시작한다.

### 최초 생성 판정

- 첫날 Standard는 숙소를 먼저 방문한 뒤 관광하고 숙소로 복귀한다.
- 첫날 CarryME 여행자는 숙소를 먼저 방문하지 않고 관광한 뒤 같은 숙소로 복귀한다.
- 숙박일의 CarryME 짐은 실제 숙소에 여행자보다 먼저 또는 같은 시각에 도착할 수 있다.
- 마지막 날 Standard와 CarryME 여행자는 모두 최초 출발지로 복귀한다.
- 마지막 날 CarryME 짐은 최초 출발지에 여행자보다 먼저 또는 같은 시각에 도착할 수 있다.
- 같은 날짜의 Standard와 CarryME는 동일한 시작점과 종료점을 가진다.
- 선택한 이동 수단이 모든 대표 이동 구간에 일관되게 적용된다.
- 대중교통 접근이 어려운 AI 추천 중간 장소는 목적 지역 안의 대안으로 조정하거나 제외할 수 있다.
- 사용자가 지정한 출발지와 목적 지역은 유지한다.
- 도보 추정 구간이나 일부 경로 실패가 있으면 절약시간을 숨긴다.

## 10. 반대 이동 수단 경로 재계산

### 재계산 시 바뀌어야 하는 항목

- 일정 전체의 이동 수단 표시
- 모든 시간표 이동 이벤트의 이동 방식
- 구간별 이동시간과 출발·도착 시각
- 일차별 및 전체 이동시간
- Standard와 CarryME의 절약시간 또는 숨김 상태
- 경로 요약, 지도 경로선, 대중교통 탑승·하차 정보

### 재계산 시 보존해야 하는 항목

- 최초 출발지와 마지막 날 최종 복귀지
- 목적 지역
- 여행 기간과 일차 수
- 방문 장소와 방문 순서
- 숙박일과 숙소
- Standard와 CarryME의 역할 차이
- 재계산 대상 일정의 장소·날짜·대화 연결 관계

### 원자성과 실패 처리

- `경로 다시 계산`은 장소와 일정 구조를 새로 생성하지 않고 선택한 이동 수단의 경로와 시간만 다시 계산한다.
- 대중교통 경로가 없다는 이유로 자동차 시간을 조용히 대신 사용하지 않는다.
- 일부 구간만 성공한 상태를 전체 성공으로 표시하지 않는다.
- 재계산 중에는 부분 갱신된 시간표, 절약시간, 지도 경로를 완료 결과로 노출하지 않는다.
- 재계산이 실패하면 마지막으로 성공한 전체 결과를 보존하고 실패한 이동 수단으로 표시만 바꾸지 않는다.
- 재계산 버튼을 연속으로 눌러도 중복 저장이나 서로 다른 결과의 덮어쓰기가 발생하지 않는다.
- 재계산 성공 후 새로고침해도 선택한 이동 수단, 시간표, 지도, 절약시간이 유지된다.
- 재계산 후 현재 URL, 저장 데이터, 공유 링크, 새로고침 결과가 동일한 일정 버전을 가리킨다.
- 자동차와 대중교통 정보가 한 일정에 혼합되어 남지 않는다.
- 재계산 후 다시 원래 이동 수단으로 되돌려도 장소와 날짜 구조가 손상되지 않는다.

## 11. 완료 판정 게이트

### 필수 통과

- 단위 및 계약 테스트가 통과한다.
- 자동차와 대중교통 경로 최종화 테스트가 통과한다.
- GPTs와 앱의 동일 시나리오 결과가 계약상 일치한다.
- 고정 프롬프트 3종과 최초 이동 수단 2종을 각 채널에서 반복 실행해 간헐 실패가 없는지 확인한다.
- 모든 최초 생성 결과에서 반대 이동 수단 재계산을 한 번 수행한다.
- 생성된 모든 일정이 날짜, 출발점, 종료점, 배송 시간, 절약시간 기준을 통과한다.
- 상세 링크와 지도 동작을 실제 브라우저에서 확인한다.
- 실패 요청의 운영 로그에서 원인을 추적할 수 있다.
- 위 항목 중 하나라도 실패하면 배포 완료로 판정하지 않는다.

### 빠른 회귀 게이트

- 고정 프롬프트 3종 × 최초 이동 수단 2종 × 채널 2종을 각 1회 실행한다.
- 총 12회 일정 생성과 12회 반대 이동 수단 재계산을 검증한다.
- 빠른 회귀 게이트는 구현 중 및 PR 검증에 사용하며 한 건이라도 실패하면 다음 단계로 진행하지 않는다.

### 최종 배포 게이트

- GPTs: 고정 프롬프트와 최초 이동 수단 조합별 3회 연속 성공
- ChatGPT 앱: 고정 프롬프트와 최초 이동 수단 조합별 3회 연속 성공
- 총 36회 일정 생성과 36회 반대 이동 수단 재계산을 검증한다.
- 최초 생성 36건과 재계산 결과 36건, 총 72개 상태가 필수 계약을 모두 통과해야 한다.
- 같은 프롬프트의 결과 장소는 달라질 수 있지만, 이 문서의 동선·시간·저장 계약은 매번 동일하게 지켜져야 한다.

### 검증 증거

각 실행마다 다음 값을 남긴다.

- 채널과 대화 URL
- 사용한 첫 프롬프트와 이동 수단 답변
- 생성된 일정 ID와 상세 링크
- 최초 생성 이동 수단과 반대 재계산 이동 수단
- 생성 시간과 재계산 시간
- 일차별 시작점, 종료점, 숙소
- 짐 배송 목적지와 도착 시각
- Standard와 CarryME 이동시간 및 절약시간 표시 상태
- 성공 또는 실패 판정과 실패 단계
- 운영 로그 추적 식별자

## 12. 확정 필요 사항

다음 수치는 아직 사용자와 확정하지 않았으므로 배포 차단 기준으로 사용하지 않는다.

- 자동차 일정 생성 목표 응답시간과 최대 허용시간
- 대중교통 일정 생성 목표 응답시간과 최대 허용시간
- 외부 API의 일시적 장애를 허용할 반복 성공률 또는 기간 기준
- 자동 재시도 횟수와 전체 요청 제한시간
- 2박 이상 일정에서 숙소가 변경될 때 CarryME가 짐을 새 숙소로 옮기는 상세 시간 계약
- 경로 재계산 결과를 같은 일정 ID의 새 버전으로 저장할지 별도 일정 ID로 저장할지 여부

수치가 확정되기 전에도 단계별 처리시간은 로그로 측정할 수 있어야 한다.

## 13. 현재 확인된 실패 사례

- 동탄호수공원에서 남해로 이동하는 일정에서 짐이 출발 10분 뒤 숙소에 도착한 것으로 표시됐다.
- 부산 1박 2일 일정의 첫날 CarryME 동선이 감천문화마을에서 끝나고 숙소 복귀가 누락됐다.
- Standard와 CarryME의 종료점이 다른 상태에서 약 28분 절약이 표시됐다.
- 출발지, 목적 지역, 기간, 이동 수단이 모두 입력됐지만 장소 검색 오류를 더 구체적인 사용자 프롬프트가 필요한 것처럼 안내했다.
- 일정 생성 과정에 여러 AI 및 장소 검색 호출이 직렬로 포함되며, 단계별 처리시간 기준이 없어 체감 성능 저하를 완료 판정에서 걸러내지 못했다.

## 비목표

- 관광지 추천 결과를 매번 동일하게 고정하는 것
- 외부 지도 서비스가 제공하지 않는 도보 경로를 실제 길안내처럼 표시하는 것
- 데모 촬영만을 위해 운영 데이터 계약을 우회하는 하드코딩
- 화면에 오류를 숨기고 잘못된 일정이나 절약시간을 성공으로 반환하는 것

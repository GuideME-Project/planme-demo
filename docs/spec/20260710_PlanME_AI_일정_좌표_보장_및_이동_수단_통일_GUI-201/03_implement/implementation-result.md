# 구현 결과

## 결론

GUI-201의 Core·MCP·REST·웹 변경과 모의 검증을 완료했다. 신규 일정은 출발지와 사용자 목적지를 AI 생성 전에 확정하고, 최종 장소는 좌표와 검색 출처가 있어야 저장된다. 이동 수단은 일정 전체의 `자동차(drive)` 또는 `대중교통(transit)` 하나로 통일된다.

## 주요 변경

- 네이버 지역 검색 후보와 주소 좌표 변환을 단일 장소 계약으로 정규화했다.
- OpenAI 도구는 `search_naver_places` 하나만 노출하며 반경·주변 검색을 제거했다.
- 출발지와 목적지를 고정하고 마지막 복귀지를 출발지로 구성했다.
- 중간 장소는 직접 검색 후 AI 대체 검색을 최대 2회 수행하고 실패하면 두 경로와 타임라인에서 제외한다.
- 준비 단계에서 이동 수단 누락 시 확정 문구와 자동차·대중교통 선택지를 반환한다.
- MCP Zod, GPTs Actions REST 검증, OpenAPI, 응답에 같은 이동 수단 계약을 적용했다.
- 웹은 `POST /api/places/search`만 사용하며 Google 자동완성·상세 조회·경로 확인 route를 제거했다.
- 웹 편집기는 일정 전체 이동 수단 선택기 하나만 두고 구간별 선택과 사용자용 도보를 제거했다.
- 선택 날짜의 Standard·CarryME를 같은 이동 수단으로 각각 계산하며 한쪽 실패를 다른 경로로 복제하지 않는다.
- 지도는 공급자가 돌려준 실제 path만 그리며 stop 직선 경로를 만들지 않는다.
- 고정 데모 데이터도 좌표·출처·역할·이동 수단 계약을 갖도록 정규화했다.

## 구현 중 확인한 회귀와 수정

1. 목적지 `남해`가 `남해 독일마을`을 같은 장소로 오인해 중간 장소를 덮어쓰는 문제를 발견했다. 목적지 일치를 정규화된 정확 일치로 제한했다.
2. AI 초안의 첫 stop을 무조건 출발지로 덮어쓰는 문제를 발견했다. 실제 출발지 표식 또는 정확 일치일 때만 교체하고, 아니면 출발지를 앞에 추가한다.
3. 고정 데모의 Standard stop에 역할·출처가 없어 편집 버튼이 항상 차단되는 문제를 발견했다. 데모도 신규 hard gate 계약으로 보강했다.

## 설계 대비 차이

- 사용자 확정에 따라 네이버 지역 검색도 `NAVER_MAPS_CLIENT_ID`, `NAVER_MAPS_CLIENT_SECRET` 변수명을 읽는다. 실제 키 권한이 지역 검색 API와 맞는지는 별도 실제 호출 검증이 필요하다.
- 사용자 목적지가 AI 결과에 없으면 현재 코드는 확정 anchor를 결정적으로 삽입한다. 별도 AI 교정 호출은 하지 않는다.
- 선택 날짜 결과 상태는 현재 화면 컴포넌트 상태로 관리한다. 날짜별 영구 캐시 구조는 이번 범위에 포함하지 않았다.

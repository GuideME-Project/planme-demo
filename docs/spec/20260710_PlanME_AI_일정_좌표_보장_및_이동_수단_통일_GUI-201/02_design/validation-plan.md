# 검증 계획

## 결론

검증은 `계약·단위 테스트 → MCP·웹 빌드 → 웹 상호작용 모의 테스트 → 실제 네이버 자동차 일정` 순서로 진행한다.
대중교통은 이번 범위에서 모의 응답으로 계약만 확인하고 실제 ODsay 호출은 하지 않는다.

최종 실제 시나리오는 `동탄 → 경주월드 → 동탄, 1박 2일, 자동차`다.
AI 생성 결과의 모든 남은 장소에 좌표와 검색 출처가 있어야 하고, Standard와 CarryME 모두 네이버 자동차 경로 계산에 성공해 실제 도로 경로선이 지도에 표시돼야 한다.

## 검증 원칙

- 사용자 지정 출발지·목적지 계약과 AI 중간 행선지 정책을 분리해 테스트한다.
- 전체 이동 수단 원본 값과 공급자 내부 세부 구간을 분리해 테스트한다.
- Standard·CarryME 성공·실패 상태를 독립적으로 검증한다.
- 모의 테스트 통과 전 실제 외부 API를 호출하지 않는다.
- 실제 호출 전 대상 API와 예상 호출 범위를 알리고 승인된 범위에서 실행한다.
- 실패 시 다른 경로를 복제하거나 직선을 그려 성공으로 보이게 하지 않는다.

## 1. 일정 준비와 계약 테스트

### 이동 수단 질문

- `transportMode` 생략: `missingSlots`에 이동 수단이 들어간다.
- 다른 필수 입력 완료·이동 수단 생략: 아래 문구를 반환한다.

```text
일정 안내는 자동차와 대중교통만 지원합니다. 어떤 이동 수단으로 안내할까요?
```

- 자동차(`drive`) 명시: 이동 수단을 다시 묻지 않는다.
- 대중교통(`transit`) 명시: 이동 수단을 다시 묻지 않는다.
- 자동차·대중교통이 혼합돼 ChatGPT가 값을 확정하지 못한 경우: 값을 생략하고 다시 묻는다.
- `walk` 또는 임의 값: MCP·REST 입력 계약이 거부한다.

### MCP와 GPTs Actions 일치

- `start_planme_planning` 입력·출력에 optional 전체 이동 수단이 있다.
- `recommend_planme_itinerary` 입력에는 required 전체 이동 수단이 있다.
- REST/OpenAPI의 enum, required, 질문 slot, normalized input이 MCP와 일치한다.
- 목적지 설명이 지역·도시로 제한되지 않고 `경주월드` 같은 사용자 지정 장소를 허용한다.
- 기존 호출 fixture가 새 필수 필드를 명시하도록 갱신된다.

## 2. 장소 검색과 좌표 보장 테스트

### 네이버 후보 정규화

- 지역 검색의 장소명 HTML 강조 태그가 제거된다.
- `mapx`가 경도, `mapy`가 위도로 정규화된다.
- 유효하지 않은 좌표는 후보에서 제외된다.
- 도로명 주소가 없으면 지번 주소를 사용한다.
- 후보에 `coordinate`, `placeSource`, `placeSourceRef`가 모두 있다.
- Google `placeId`를 생성하지 않는다.
- 지역 검색 빈 결과와 주소 좌표 변환 후보가 구분된다.

### 고정 장소

- 출발지 `동탄`은 목적지 `경주` 지역 후보로 검색하지 않는다.
- 넓은 지역인 동탄은 대표 좌표를 자동 선택할 수 있다.
- 목적지 `경주월드`는 AI 호출 전에 네이버 후보로 확정된다.
- 하나라도 확정되지 않으면 OpenAI 일정 생성과 링크 저장을 호출하지 않는다.
- 사용자에게 더 정확한 장소명 또는 주소를 요청한다.
- AI가 다른 출발지·목적지 좌표를 반환해도 선검증 anchor로 덮어쓴다.
- Standard·CarryME 모두 경주월드를 포함한다.
- 첫날 출발지와 마지막 날 복귀지는 같은 동탄 좌표를 사용한다.

### 중간 행선지와 숙소

- 첫 검색 성공: 기존 장소에 좌표와 출처를 반영한다.
- 첫 검색 실패·첫 대체 성공: 새 장소명·좌표·출처로 교체한다.
- 첫 대체 실패·두 번째 대체 성공: 두 번째 후보를 반영한다.
- 두 번 모두 실패: Standard·CarryME stop과 관련 타임라인·경로 문구에서 제외한다.
- 제외 후 출발지와 목적지만 남아도 일정을 생성한다.
- 숙소 후보도 네이버 검색만 사용한다.
- Google 텍스트 검색과 주변 검색 함수는 호출되지 않는다.

### 최종 hard gate

- 모든 최종 stop 좌표가 유한 숫자와 유효 범위를 만족한다.
- 모든 최종 stop에 허용된 검색 출처와 비어 있지 않은 `placeSourceRef`가 있다.
- 사용자 지정 목적지가 최소 한 번 포함된다.
- 출발·복귀 좌표가 선검증한 출발지와 일치한다.
- 중간 장소 실패는 제외 가능하지만 출발지·목적지 실패는 저장 불가다.

## 3. AI 도구와 정규화 테스트

- OpenAI 도구 목록에 `search_naver_places`만 장소 검색 함수로 노출된다.
- `search_places_nearby`와 반경 입력이 없다.
- AI prompt에 선검증 출발지·목적지 좌표와 전체 이동 수단이 포함된다.
- AI structured output이 stop별 이동 수단을 결정하지 않거나, 반환하더라도 서버가 전체 이동 수단으로 덮어쓴다.
- 사용자 목적지 누락 시 초안 교정 요청을 한 번 수행한다.
- 교정 후에도 목적지가 없으면 링크를 생성하지 않는다.
- 장소 대체 시도는 stop별 최대 2회며 OpenAI 도구 반복 상한과 충돌하지 않는다.

## 4. 웹 장소 편집 테스트

### 검색

- 2자 미만 입력은 외부 호출을 하지 않는다.
- 약 300ms 안에 계속 입력하면 마지막 검색만 실행된다.
- 새 검색 시 이전 요청이 취소된다.
- Google 자동완성 세션 토큰과 오사카 중심 좌표를 사용하지 않는다.
- 후보 선택 한 번으로 이름·주소·좌표·출처가 모두 반영된다.
- 장소명을 다시 입력하면 이전 좌표·`placeId`·출처가 모두 제거된다.
- 후보를 선택하지 않고 버튼을 누르면 `장소를 선택해 주세요`를 표시하고 경로를 호출하지 않는다.

### 이동 수단

- 일정 전체 선택기 하나만 표시한다.
- 선택지는 자동차·대중교통이다.
- 행선지별 이동 수단 선택기와 사용자용 도보 선택지가 없다.
- 이동 수단을 바꾸면 Standard·CarryME가 모두 재계산 필요 상태가 된다.
- 이동 수단 변경만으로 네이버·ODsay 호출이 발생하지 않는다.

### 재계산과 부분 실패

- 버튼을 누르면 Standard와 CarryME가 같은 이동 수단을 사용한다.
- 두 일정은 각자의 stop 목록과 결과 상태를 유지한다.
- 둘 다 성공하면 각각의 실제 경로선을 표시한다.
- Standard만 실패하면 CarryME 성공 결과를 유지한다.
- CarryME만 실패하면 Standard 성공 결과를 유지한다.
- 실패 영역에는 `경로를 확인하지 못했습니다`를 표시한다.
- 실패한 결과에 다른 일정의 경로를 복제하지 않는다.
- 공급자 path가 없을 때 stop 직선을 실제 경로선처럼 표시하지 않는다.

## 5. 자동 검증 명령

구현 후 저장소 루트에서 다음 순서로 실행한다.

```bash
npm run test:actions
npm run test:mcp
npm --workspace @planme/core run build
npm --workspace @planme/mcp run typecheck
npm --workspace @planme/web run build
npx playwright test apps/web/e2e/destination-editor-recorded-flow.spec.ts --project=chromium
```

- 기존 Google autocomplete/details mock과 구간별 혼합 이동 수단 fixture는 네이버 검색·일정 전체 이동 수단 fixture로 교체한다.
- 저장소 자동화 브라우저 테스트는 회귀 확인에 사용한다.
- 실제 화면 확인은 로그인·세션이 있는 Edge 또는 앱 내 브라우저에서 별도로 수행한다.
- 실패한 명령과 원인을 숨기지 않고 기록한다.

## 6. 실제 네이버 자동차 시나리오

### 사전 조건

1. 모의 계약 테스트와 빌드가 모두 통과한다.
2. 원본 체크아웃의 gitignored 런타임 파일을 민감값 출력 없이 현재 worktree에 준비한다.
3. 현재 worktree 코드로 MCP와 웹 서버를 다시 시작한다.
4. 기존 `8787` 포트의 오래된 MCP 프로세스가 새 코드를 가리지 않는지 확인한다.
5. 실행 전 네이버 지역 검색·주소 좌표 변환·Directions·OpenAI의 예상 호출 범위를 알린다.

### 입력

```text
출발지: 동탄
사용자 지정 목적지: 경주월드
기간: 1박 2일
전체 이동 수단: 자동차
복귀지: 동탄
```

### MCP·생성 결과 확인

- 준비 단계가 이동 수단을 다시 묻지 않는다.
- 출발지와 목적지가 AI 생성 전에 좌표·출처를 가진다.
- 생성 결과가 준비 완료 상태이며 상세 링크를 반환한다.
- Standard·CarryME 모두 경주월드를 포함한다.
- 마지막 날 복귀지가 동탄이다.
- 모든 최종 stop에 좌표와 `placeSourceRef`가 있다.
- 모든 대표 stop 이동 수단과 저장 일정 전체 이동 수단이 자동차다.
- 좌표 없는 중간 장소는 최대 2회 대체 후 교체 또는 제외돼 최종 결과에 남지 않는다.

### 웹 지도 확인

- 생성된 신규 상세 링크를 Edge 또는 앱 내 브라우저로 연다.
- 전체 이동 수단 선택기가 자동차로 표시된다.
- 사용자용 도보와 행선지별 이동 수단 선택기가 없다.
- 필요하면 중간 장소를 검색해 네이버 후보를 선택한다.
- 장소 또는 이동 수단을 바꾼 뒤 버튼 전에는 경로 호출이 없다.
- `경로 다시 계산` 버튼을 누르면 Standard·CarryME 자동차 경로가 각각 계산된다.
- 두 결과의 시간·거리와 네이버 실제 도로 경로선이 지도에 표시된다.
- 경로선은 면 polygon이나 stop 직선이 아니라 공급자 좌표를 이은 polyline이다.

## 7. 대중교통 모의 계약 검증

실제 ODsay 호출은 이번 검증 범위에서 제외한다.

- 전체 이동 수단 `transit`이 MCP·저장·웹 요청까지 보존된다.
- Standard·CarryME 모두 ODsay 경로 adapter를 선택한다.
- 공급자 내부 접근·환승·하차 도보 구간은 유지된다.
- 내부 도보 구간이 일정 전체 이동 수단을 `walk`로 바꾸지 않는다.
- ODsay 성공·실패 mock으로 두 일정의 부분 실패 상태를 검증한다.

## 완료 기준

- 자동 계약 테스트·빌드·웹 회귀 테스트가 통과한다.
- 신규 일정 생성에서 Google Places와 주변 검색 호출이 없다.
- `동탄 → 경주월드 → 동탄, 1박 2일, 자동차` 실제 생성이 완료된다.
- 최종 일정의 모든 장소에 좌표와 검색 출처가 있다.
- Standard·CarryME가 같은 전체 이동 수단으로 각각 네이버 길안내에 성공한다.
- 두 실제 도로 경로선이 네이버 지도에 표시된다.
- 한쪽 실패 시 성공 경로 보존·실패 문구·무경로선 처리가 계약대로 동작한다.

## 중단 기준

- 출발지 또는 사용자 지정 목적지를 네이버로 확정할 수 없다.
- 인증 정보가 누락됐거나 원본 체크아웃과 현재 worktree의 런타임 파일 경계를 안전하게 확인할 수 없다.

- 신규 일정에 좌표·검색 출처 없는 stop이 남는다.
- 실제 공급자 실패를 복제 경로나 직선 경로로 가리는 동작이 남아 있다.

# 외부 연동 및 운영 리스크 설계

## 결론

신규 국내 장소 검색은 네이버 지역 검색과 네이버 주소 좌표 변환만 사용한다.
자동차 경로는 네이버 Directions, 대중교통 경로는 기존 ODsay, 지도 표시는 네이버 Dynamic Map을 유지한다.
Google Places는 AI 생성과 웹 장소 편집에서 모두 제거하며 장애 시 숨은 Google fallback을 두지 않는다.

네이버 인증 정보와 원본 응답 처리는 서버에 한정한다.
브라우저에는 공개용 지도 클라이언트 식별자와 정규화된 장소·경로 데이터만 전달한다.

## 연동 목록

| 업무 목적 | 외부 기능 | 호출 위치 | 인증 경계 |
| --- | --- | --- | --- |
| 상호·관광지·숙소 검색 | [네이버 지역 검색](https://developers.naver.com/docs/serviceapi/search/local/local.md) | PlanME 서버, 웹 API route | NAVER Developers 애플리케이션 인증 |
| 주소·행정구역 좌표 확인 | [네이버 Maps Geocoding](https://api.ncloud-docs.com/docs/ai-naver-mapsgeocoding-geocode) | PlanME 서버 | Naver Cloud Platform 인증 |
| 자동차 경로 계산 | 네이버 Maps Directions | 웹 API route | Naver Cloud Platform 인증 |
| 대중교통 경로 계산 | ODsay | 웹 API route | ODsay 서버 인증 |
| 지도와 경로선 표시 | 네이버 Dynamic Map | 브라우저 | 공개용 지도 클라이언트 식별자 |
| 장소 후보 판단·일정 생성 | OpenAI Responses API 사용자 정의 함수 | PlanME 서버 | OpenAI 서버 인증 |

네이버 지역 검색과 Naver Cloud Maps API는 같은 회사의 서비스지만 인증 체계와 키가 같다고 가정하지 않는다.
구현 전 원본 체크아웃 `.env`의 실제 변수 이름과 현재 코드의 사용 위치만 확인하고, 값은 출력하거나 설계 문서에 기록하지 않는다.

## 민감값 처리

- 네이버 지역 검색 클라이언트 비밀값, Naver Cloud 인증 비밀값, ODsay 키, OpenAI 키는 서버 전용이다.
- 브라우저 번들, HTML, 로그, 오류 응답에 서버 전용 값을 포함하지 않는다.
- 현재 worktree에 런타임 파일이 필요하면 원본 체크아웃에서 민감값 출력 없이 복사하는 절차를 사용한다.
- `.env` 원문을 확인 결과나 테스트 로그에 붙이지 않는다.
- 네이버 원본 오류 응답에 요청 식별 정보가 있어도 사용자 응답에는 내부 오류 코드만 노출한다.

## 네이버 지역 검색 정규화 리스크

### 위치 편향이 없는 텍스트 검색

네이버 지역 검색은 특정 중심 좌표와 반경을 받는 주변 검색으로 설계하지 않는다.
검색어에 지역명과 장소명을 함께 넣고, AI는 반환된 후보 안에서 사용자 목적·지역·장소 종류에 맞는 결과를 선택한다.

예시:

```text
경주 황리단길 한식
경주 보문단지 숙소
동탄
```

### 좌표 변환

지역 검색의 `mapx`, `mapy`는 [WGS84 좌표계 공지](https://developers.naver.com/notice/article/12567)에 따라 정규화한다.
응답 예시와 자리수를 근거로 경도·위도 값의 스케일을 변환한 뒤 범위를 검증한다.
변환된 값이 국내 범위를 크게 벗어나거나 유효 숫자가 아니면 후보에서 제외한다.

### 안정적인 장소 식별자 부재

Google `placeId`와 동일한 영속 식별자가 있다고 가정하지 않는다.
`placeSourceRef`는 검색 공급자, 정규화 주소 또는 링크, 좌표를 조합해 생성하고 다음 용도로만 사용한다.

- 선택한 후보의 출처 확인
- 동일 응답·동일 좌표의 중복 후보 제거
- Standard·CarryME의 명시적 동일 장소 판단 보조
- 디버깅 시 원본 검색어와 결과 추적

네이버 데이터가 바뀌어도 영구적으로 동일한 장소를 보장하는 외부 ID로 사용하지 않는다.

## 시간 제한과 재시도

상품 정책의 `중간 행선지 최대 2회 대체`와 네트워크 재시도는 구분한다.

| 실패 종류 | 처리 |
| --- | --- |
| 잘못된 입력·인증 실패 등 4xx | 자동 재시도하지 않고 즉시 실패 처리 |
| 요청 제한 429 | 응답 지침이 있으면 짧게 한 번 재시도하거나 상위 단계에 실패 반환 |
| 일시적 서버 오류 5xx | 짧은 지연 후 한 번만 재시도 |
| 시간 초과·연결 끊김 | 한 번만 재시도 후 실패 반환 |
| 정상 응답이지만 적합 후보 없음 | 네트워크 재시도가 아니라 AI 대체 검색 횟수 1회를 사용 |

자동 재시도가 AI 대체 검색 횟수를 늘리거나 반대로 줄이지 않게 별도 카운터를 둔다.
사용자 지정 출발지·목적지 검색 실패는 일정 생성을 중단하고, 중간 행선지 실패만 최대 2회 대체 후 제외한다.

## 캐시와 호출 억제

- 서버 장소 검색은 정규화한 검색어와 결과 개수를 키로 짧은 캐시를 둘 수 있다.
- 1차 권장 만료 시간은 10분이며 구현 시 기존 캐시 도구와 테스트 가능성을 기준으로 확정한다.
- 실패 응답과 인증 오류는 캐시하지 않는다.
- 웹은 2자 미만 검색 금지, 약 300ms 입력 지연, 이전 요청 취소로 불필요한 호출을 줄인다.
- 같은 생성 요청 안의 Standard·CarryME 중복 장소는 검색 결과를 공유한다.
- 경로 계산은 이동 수단 변경 즉시 호출하지 않고 버튼 클릭 시에만 수행한다.

## 호출량 경계

정상 일정 생성의 외부 호출은 다음 범주로 나뉜다.

1. 출발지·목적지 고정 장소 검색
2. OpenAI 일정 생성과 필요 시 고정 장소 교정
3. 중간 행선지·숙소별 네이버 후보 검색
4. 실패한 중간 행선지의 대체 검색 최대 2회
5. 웹 초기 또는 버튼 재계산 시 Standard·CarryME 경로 호출

실제 호출 수는 AI가 만든 행선지 수와 대체 횟수에 따라 달라지므로 설계 문서에서 고정 수치로 단정하지 않는다.
실제 네이버 검증 전에는 예상 호출 범위와 대상 API를 사용자에게 알리고 승인 범위 안에서만 실행한다.
가격과 할당량은 구현·배포 시점의 공식 콘솔과 문서를 다시 확인한다.

## 오류 변환

### 장소 검색

```ts
type PlaceSearchErrorCode =
  | "INVALID_QUERY"
  | "PROVIDER_UNAUTHORIZED"
  | "PROVIDER_RATE_LIMITED"
  | "PROVIDER_UNAVAILABLE"
  | "NO_VALID_CANDIDATE";
```

- 웹 검색은 사용자에게 다시 시도 가능한 일반 문구를 표시한다.
- AI 생성 내부 검색은 필수 장소와 중간 장소 정책에 따라 질문·대체·제외로 변환한다.
- 공급자 응답 본문과 인증 헤더를 사용자 오류에 포함하지 않는다.

### 경로 계산

- 자동차와 대중교통 오류는 일정 종류별 `failed` 상태로 변환한다.
- Standard와 CarryME 오류를 합쳐 전체 성공 또는 전체 실패로 만들지 않는다.
- 경로 공급자 실패를 다른 일정 종류의 결과나 임의 직선으로 보완하지 않는다.

## 로그와 사용량 기록

기존 사용량 기록과 같은 경계에서 최소 정보만 남긴다.

```ts
type ExternalUsageEvent = {
  event:
    | "naver_local_search_request"
    | "naver_geocode_request"
    | "naver_directions_request"
    | "odsay_transit_request"
    | "openai_request";
  outcome: "success" | "empty" | "failed";
  latencyMs: number;
  candidateCount?: number;
  errorCode?: string;
};
```

- 검색어 전체가 개인정보 또는 상세 주소일 수 있으므로 기본 로그에 원문을 남기지 않는다.
- 인증값, 원본 응답, OpenAI 전체 prompt·response는 기록하지 않는다.
- 중간 행선지 교체·제외는 장소 해석 로그에 시도 번호와 결과만 남긴다.
- 개발 진단에 검색어가 필요하면 마스킹 또는 명시적인 로컬 디버그 옵션을 사용한다.

## 장애와 rollback

네이버만 사용한다는 제품 결정을 지키기 위해 런타임 Google fallback은 두지 않는다.

- 네이버 장소 검색 장애 시 필수 장소가 필요한 신규 일정 생성을 완료하지 않는다.
- 웹 장소 편집은 기존 선택 장소를 유지하고 새 검색 실패를 알린다.
- 배포 회귀는 코드 배포 rollback으로 대응한다.
- rollback으로 Google Places가 다시 활성화될 수 있는 이전 배포를 선택할 때는 제품 요구와 개인정보·비용 영향을 별도로 확인한다.
- 기능 flag가 필요하면 `네이버 실패 시 Google 사용`이 아니라 신규 장소 검색 기능 자체의 활성·비활성 경계로 둔다.

## 대안과 기각 이유

### 네이버 실패 시 Google Places 자동 사용

기각한다. 사용자가 신규 장소 검색은 네이버만 쓰기로 확정했고, 공급자별 좌표·식별자·비용 계약이 다시 섞인다.

### 네이버 원본 응답을 브라우저에 전달

기각한다. 공급자 세부 형식이 UI에 결합되고 불필요한 데이터와 오류 정보가 노출된다.

### 모든 검색 결과 장기 캐시

기각한다. 장소 정보 변경을 늦게 반영하고 현재 저장소에 영속 캐시 운영 근거가 없다.

## 리스크

- 네이버 지역 검색 공식 문서 페이지가 일시적으로 렌더링되지 않을 수 있어 공식 Swagger·공지와 실제 모의 응답을 함께 검증해야 한다.
- 네이버 Developers와 Naver Cloud Platform 인증이 분리돼 있어 기존 지도 키만으로 지역 검색이 된다고 가정하면 실패한다.
- 지역 검색에 중심 좌표·반경이 없으므로 동명이인 후보 선택 품질은 검색어와 AI 판단에 영향을 받는다.
- 검색어에 상세 주소가 들어가면 로그·오류 추적 과정에서 개인정보가 남을 수 있다.
- 대체 검색과 OpenAI 교정이 겹치면 호출량과 응답 시간이 늘어날 수 있다.

## 검증 연결

- 브라우저 번들·응답·로그에 서버 인증값이 없는지 확인
- Google Places와 주변 검색 함수가 호출되지 않는지 확인
- 지역 검색 좌표 정규화와 HTML 태그 제거 확인
- 4xx 무재시도, 429·5xx·시간 초과 제한 재시도 확인
- 중간 장소 2회 대체와 네트워크 재시도 카운터 분리 확인
- Standard·CarryME 부분 실패가 독립 상태로 남는지 확인
- 실제 호출 전 예상 범위 고지와 민감값 비출력 확인
